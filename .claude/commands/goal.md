あなたは necoder の実装エージェント。**ドキュメントだけを頼りに次の1歩を自走**せよ。ユーザーへの質問はブロッカー時のみ。

引数: `$ARGUMENTS`（空なら ROADMAP の順序に従う。指定があればそのタスク/マイルストーンを優先）

## 手順

1. **現在地の把握**（必ず全部読む）:
   - `docs/ROADMAP.md` — 未チェックの受入条件（上から）
   - `docs/JOURNAL.md` — 直近エントリの「学び/罠」「次」
   - `git status` / 直近コミット（git 化されていれば）
2. **タスク選定**: 未完マイルストーンの未チェック項目のうち依存順で最初の1つ（大きければ半日で終わる粒度に割る）。着手前に選定理由を1行報告
3. **実装**: 以下が正。乖離したら実装でなく文書を疑い、文書側の修正を提案:
   - 設計: `docs/ARCHITECTURE.md`（crate 配置・依存方向・型契約・移植作法）
   - 見た目: `docs/UI-SPEC.md` + `mock/index.html`（色の許可リスト厳守）
   - 規約・検証ループ: `CLAUDE.md`（zed/ 変更禁止・t! 規律・unwrap 回避 等）
   - zed からの移植は出典コメント必須。collab/CRDT/テレメトリ経路は落とす
4. **検証**（受入条件を実際に満たすまで完了と言わない）:
   - `cargo check` → `cargo test` → UI 変更なら `./scripts/screenshot-app.sh` の PNG を Read して目視
   - ベンチ導入後は性能予算（Zed 比 ~80%）の退行チェック
5. **記録**:
   - `docs/ROADMAP.md` の該当チェックボックスを更新（満たした分だけ）
   - `docs/JOURNAL.md` 末尾に1エントリ追記（やったこと/学び・罠/次）
6. **報告**: 変更ファイル一覧・受入条件の充足状況・次の1歩を簡潔に

## 禁止事項

- `FEATURES.md` のタグ（MVP/v1/later/never）変更 — ユーザー管理
- `zed/` 配下の変更・`git pull`
- ROADMAP 外の先回り実装（気づきは JOURNAL の「次」に書くに留める）
- 検証を通さずにチェックを入れること
