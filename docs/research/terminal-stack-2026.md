# ターミナル原理主義スタック — 競合としての読みと参照優先度

きっかけ: 2026-07-17、「VSCode を捨てて Ghostty + zellij + yazi + lazygit + fzf/ripgrep + Claude Code に寄せた」という構成の共有。
この文書は **その構成を necoder の競合として読んだときに何が言えるか**と、**どのツールを実装の手本にするか（優先度）**。
関連: [`feature-matrix.md`](./feature-matrix.md)（3エディタ横断）/ [`../ROADMAP.md`](../ROADMAP.md) M11・M12 / [`../BACKGROUND.md`](../BACKGROUND.md)（並行エージェントの痛点）/ [`../UI-SPEC.md`](../UI-SPEC.md) §6（スレッド色貫通）。

---

## 0. なぜ「ただの趣味構成」でなく競合なのか

VSCode を捨てる層は2方向に逃げる。**Zed 方向**（速い統合 GUI）と、この**ターミナル方向**（TUI を束ねて GUI を捨てる）。
necoder の想定ユーザー＝「速さと AI エージェントを本気で使う開発者」は、後者と**完全に重なる**。しかもこの構成は最後に Claude Code を据える＝**necoder と同じ賭け（AI エージェントを中心に置く）を、GUI 無しでやっている**。だから趣味ではなく直接の対抗馬として扱う。

売り文句は「メモリ節約」「起動が爆速」「エディタを捨ててターミナルに寄せる」。この3語がそのまま necoder の性能予算・ネイティブ路線の裏返しになっている。

## 1. 各ツール → necoder の対応（新ネタか、答え合わせか）

| 相手 | 役割 | necoder の対応物 | 判定 |
|---|---|---|---|
| **Ghostty** | 端末（起動速い・低メモリ） | 性能予算（Zed 比 ~80%・起動 ~100ms cold） | **答え合わせ**。ネイティブで既に勝ってる領域。ただしメモリの数字は未計測（§4） |
| **zellij** | 分割・セッション | 分割ペイン・ドック・タブ・hot exit（M10） | **答え合わせ**。GUI の窓/タブ/状態復元が session の役を既に果たす |
| **yazi** | ファイラ（プレビュー・非同期） | エクスプローラ（M5・Miller カラム） | **半分新ネタ**。非同期優先は M10 の非ブロッキング化と同じ思想。プレビュー列だけが未所持の UI 案 |
| **lazygit** | git（可読な TUI） | git status/gutter（M8）＋ **hunk stage・パネル・blame は未（M11/M12）** | **新ネタ最大**。未実装かつ難所の直接の手本 |
| **fzf + ripgrep** | 曖昧選択・検索 | 使い回し Picker（M3）・search crate | **答え合わせ**（思想は既に内在）。ただし ⌘P は in-process（§4） |
| **Claude Code** | AI コーディング | ACP スレッド（M4）＋ 色/通知（M12） | **中核の賭けそのもの**。§2 参照 |

結論の骨: **新しく学べるのは lazygit と（プレビュー列という一点で）yazi だけ**。残りは necoder が既に等価物を持っているので「賭けが当たっている」証拠として読む。

## 2. この構成が晒す痛み = M12 の存在証明

裏返すと弱点がそのまま出る。**Claude Code が zellij の1ペインでしかない**こと。

worktree×3 で3セッション並走した瞬間に失われるもの:
- どのペインが**どのプロジェクト/ブランチ**か（宛先チップが無い）
- 各セッションが**何トークン**使ったか（常時メーターが無い）
- **さっきの変更は誰の仕業か**（プロセスが別々で、ファイルとセッションが繋がらない）

これは [`../BACKGROUND.md`](../BACKGROUND.md) の原点痛点そのもので、M12 の受入（「色と通知だけで迷子にならず、全変更を diff レビュー→ checkpoint で巻き戻す」）が丸ごと答えになっている。**この投稿は necoder の売り文句を敵側の視点で書いてくれた**＝ポジショニングの一次資料として価値がある。

そして彼らが**構造的に絶対できない**のが色貫通（[`../UI-SPEC.md`](../UI-SPEC.md) §6）。tmux/zellij のペインは別プロセスだから「yazi のツリーに、lazygit の staging や Claude Code のスレッド色が乗る」は原理的に不可能。**一貫性（cross-tool の色・スレッド・帰属の貫通）が necoder の堀**であり、束ねただけのスタックには埋められない。

## 3. 「一番いいのは何か」— 参照優先度

投稿の枠をそのまま飲まず、necoder（**キーボード主・色主・ネイティブ GUI**）にとっての転用価値で並べ直す。

1. **lazygit（最優先・ただし GUI 用に三角測量）** — 理由は「git パネル・hunk/行単位 stage・blame が M11/M12 の未実装かつ難所」で、lazygit はまさに *git をキーボードで可読にする* 問題を最良に解いたから。パネル配置（status / files(staged↑unstaged↓) / branches / commits / stash を常時表示、Tab か数字でフォーカス）と、`space` で hunk、ファイルに入って**行単位 stage**、`x` メニューで全操作を発見可能にする設計がそのまま情報設計の手本になる。
   **ただし lazygit は TUI**。モーダル/hjkl/固定ペインをそのまま GUI に写すと負ける。GUI 版の三角測量として:
   - **Sublime Merge** — *ネイティブ GUI* の git クライアントの金字塔。キーボード＋マウス・巨大 repo でも即時・行単位 stage/blame/コミット差分検索。**necoder も GUI なので相互作用モデルが 1:1 で転用できる**。「速い GUI git はどう振る舞うか」はここが基準。
   - **magit（Emacs）** — 最深。**section 折り畳み**（hunk がファイルの下に畳める木として1バッファに並ぶ）と **transient メニュー**（全フラグをキーで発見）。折り畳みモデルは lazygit の固定ペインより **necoder のエディタ中心の作りに馴染む**可能性がある。
   → 実装時は **lazygit（キー IA と hunk stage の粒度）＋ Sublime Merge（GUI の手触り）＋ magit（折り畳みと発見性）** を突き合わせる。単一の模写はしない。

2. **fzf の思想（最重要の原則・ただし既に自分のもの）** — fzf の本質はツールでなく **「あらゆるリストを曖昧選択の1プリミティブに通す」普遍性**（ファイル・ブランチ・履歴・プロセス、全部同じ UI）。necoder は M3 で「1つの fuzzy Picker を全モーダルで使い回す」と既にこれを採用済み。だから *学ぶ* のではなく ***どこまでも広げる*** のが教訓 — M13 のコマンドパレット・ブランチ切替・git アクション・シンボルジャンプ（M11 ⌘⇧O）まで全部 Picker に載せる。「一番深い原則だが、既に内在化済み」。

3. **yazi のプレビュー列（一点だけ）** — カラムビューに**プレビュー段**を足す案。ただし GUI では「開けばタブで見える」ので価値は TUI ほど高くない。優先度低。非同期優先アーキ自体は M10 で同じ結論に到達済み。

4. **Ghostty（設計でなく数字）** — 手本ではなく**性能予算の再確認**。この層は RAM で買う客なので、メモリの実測値を武器にできる（§4）。

5. **zellij（最下位）** — GUI の窓/タブ/ドック/hot exit で役割を既に吸収済み。名前付きレイアウトの発想くらい。

**一行で**: *実際に開いて読むべき唯一は lazygit（＋GUI 用に Sublime Merge/magit で補正）。fzf は「一番いい原則」だが既に Picker として持っている。*

## 4. 拾う具体アクション

- **性能予算にメモリの数字を足す**（CLAUDE.md の予算は今レイテンシ＋起動のみ）。ネイティブとはいえ LSP＋terminal＋ACP＋tree-sitter＋Turso を載せるので、`idle N MB` を測って予算化すると、この層に対する武器になる。M13 の入力レイテンシベンチと同じ CI に相乗り。
- **⌘P の巨大 repo 実測**。今は in-process 曖昧一致（[`feature-matrix.md`](./feature-matrix.md) §5 の当初方針「ripgrep 子プロセス（最安で最強）」から in-process へ逸脱している）。「fzf+rg の方が速い」と言われないために、数万ファイル級で実測し、必要なら子プロセス化を M13 で判断。
- **M11 着手時に lazygit を開く**（§3）。hunk 操作・git パネル・blame の情報設計とキー体系を Sublime Merge/magit と突き合わせてから作る。この文書を入口に。

### §4 の消化結果（2026-07-17 実測）

- **メモリ**: idle RSS **122 MB**（release・ファイル 1 枚表示・起動 8s 後。`scripts/memory-usage.sh` 新設）。起動 **~215ms**（`scripts/startup-time.sh`）。→ CLAUDE.md の性能予算に数字として記載。
- **⌘P**: in-process fuzzy の refilter を実測（`ui/examples/bench_fuzzy` 新設・zed クローン 4,194 件 + 50k 合成）。**実 repo ~0.85ms・50k 件でも ~10ms/キー = 1 フレーム（16ms）以内** → 子プロセス化（fzf/rg 方式）は不要と判断。あわせて ⌘P の列挙上限を 5,000 → **50,000** に引き上げ（列挙は背景 ~90ms・開く速さに影響なし）。10 万件級の repo が現実になったら再計測ライン。
- lazygit/Sublime Merge/magit の突き合わせは M11 実装（hunk stage・パネル・blame）で消化済み。fzf 原則（全部 Picker）も M13 の ⌘⇧P で全域到達。

## 5. 教訓

- **バンドル各部の基準は lazygit / yazi / Sublime Merge であって、VSCode の凡庸な内蔵ではない**。VSCode を捨ててこのスタックへ移る層は、内蔵が「そこそこ」だと同じ理由で necoder も捨てる。git が lazygit 未満、検索が fzf 未満なら負ける。
- **勝ち筋は機能でなく一貫性**。個々のツールは真似られても、色・スレッド・プロジェクト帰属が**全領域を貫通する**ことは、別プロセスの寄せ集めには構造的に不可能。ここに全振りする（M12）。
- この投稿は**競合であると同時に、necoder の必要性の証明**。並行エージェント時代に「エディタを捨ててターミナルへ」が本気で語られるほど、「色と通知で並行エージェントに迷わない GUI」の空白は大きい。
