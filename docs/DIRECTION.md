# necoder の方向性 — 会話から始め、成果物を見ながら作る

更新: 2026-10-27

necoder は、使いたい AI に頼み、できたものを見ながら直し、必要なところを自分でも編集できる開発環境を目指す。
標準の入口を Agent に置き、相談・制作・プロジェクトの変更・並列開発へ段階的に進める。
「色による方向感覚」「作業先の識別」「ネイティブの軽さ」は、この体験を支える基盤として維持する。

この文書は今後の製品方針と設計上の制約をまとめたもので、記載した変更は未実装。
受入条件は [ROADMAP](./ROADMAP.md#agent-first) に置く。
現行の画面・用語・セッションの仕様は [UI-SPEC](./UI-SPEC.md)、[GLOSSARY](./GLOSSARY.md)、
[CHAT](./CHAT.md)、[FLEET-V2](./FLEET-V2.md) を参照する。実装に入る単位で mock・仕様・用語を更新する。
この文書によって現行の設定や保存形式が変更されたことにはしない。

## 1. 入口を一つにする

初めて開いたときに必要なのは、依頼を書ける入力欄と、最近の会話・成果物へ戻る道。
最初の依頼の前に Chat / Fleet / Editor の用途を理解したり、Captain を任命したりする必要をなくす。
相談だけでも使え、「HTML を作って」「このプロジェクトを直して」と作業を広げられる。

目指す画面の骨格は次のとおり。寸法や配置の確定仕様ではない。

```text
会話・プロジェクト一覧  │ 選んだ会話              │ 成果物・確認
                      │                        │
＋ 新しい会話          │ 依頼・相談              │ プレビュー
最近の作業             │ 進捗・質問              │ 変更レビュー
プロジェクト           │ 結果・検証内容          │ 必要なときに開く
                      │                        │
                      │ 宛先・トークン・入力欄   │
```

- 会話は既定で一つを大きく表示する。並べる操作を選んだときに複数を表示する。
- 成果物がない場合は会話を広く使う。空のプレビューや変更ペインを常設しない。
- プロジェクトを選んでいなくても相談・単体の成果物制作を始められる。
- 複数 Task・Captain・編隊図は、並列開発が必要になったところで現れる。
- 宛先チップとトークン常時表示は維持する。色は識別に使い、状態は形・文言・動きで伝える。

「チャットに親しみがある」は入口を簡単にするための設計仮説。
画面の類似や機能の数だけで使いやすさを判断せず、依頼から成果物の確認・修正までを通して確かめる。

## 2. Agent / Editor の二つの表示へ

Agent は会話と成果物を中心に作業する表示、Editor はコードを直接読み書きする表示とする。
Editor は既定の着地面から外れても、フル機能と性能を維持し、割り当て済みのショートカットまたは
明確な操作一つで往復できるようにする。具体的なキーは既存の割り当てと照合し、UI-SPEC で確定する。

表示を切り替えても、選んだプロジェクト・ブランチ・会話・開いていた成果物を取り違えない。
necoder 自身を necoder で開発する流れも、継続して品質の確認に使う。

Fleet の Task・worktree・レビュー・統合・Captain は Agent 表示の中で利用できるようにする。
既存の `1 Task = 1 branch = 1 worktree` は維持する。一方、すべての会話を Task として作成する必要はない。
既存プロジェクト内の通常スレッドにも、相談や単体 HTML にも、新規 worktree を強制しない。

## 3. Chat は行き先として残す

独立した Chat モードは、統合と移行が完了した後に畳む。
Chat のプリセット、ファイルの保存場所、権限、履歴、再開、成果物を扱う機能は維持する。
新しいチャットエンジンや成果物専用の保存形式は作らない。

| 会話の行き先 | セッションの意味 | 主な成果物・変更先 |
|---|---|---|
| プロジェクトなし | 既存 Chat の相談用プリセットと権限 | 書類フォルダ内の会話ごとの `artifacts/` と、明示的に渡したファイル |
| プロジェクト ⎇ ブランチ | プロジェクト内の通常スレッド | 選んだプロジェクトの作業先 |
| 分離した Task | Fleet の Task と worktree | その Task の worktree |

「プロジェクトなし」にも内部の保存用フォルダはある。ユーザーにプロジェクト作成を要求しないという意味であり、
ファイルの置き場がないという意味ではない。保存先とアクセス範囲は確認できるようにする。
一覧では三つを区別でき、同じ会話を重複して表示しない。

行き先は、表示の切り替えとセッションの権限変更を混同させない形にする。
最初の送信前は行き先を選べるが、開始済みの Chat をチップ操作だけでプロジェクト権限へ昇格させない。
別の作業先へ進むときは、新しいセッションへの引き継ぎとして扱い、渡す文脈とファイルを明示する。
既存の会話の cwd やセッション ID を暗黙に変更しない。

### 軽い相談を維持する根拠

[CHAT §7](./CHAT.md#7-実機で分かったこと2026-09-19) の実測では、同じ問いに対して
Chat の文脈は 5,199 トークン・初回応答 3.1 秒、Editor と同じセッションの作り方では
28,703 トークン・4.0 秒だった。これは 2026-09-19 の条件付きの実測であり、
あらゆるモデルで同じ倍率の料金・速度になることを意味しない。
相談に不要なプロジェクト文脈やツールを載せない価値を示す基準として使い、変更後も比較する。

Chat の書き込み制限と artifact 表示の隔離は、それぞれ別に維持する。
前者はファイル操作への権限判定、後者は WebView の配信範囲・CSP 等による制限であり、
作業フォルダやプロンプトだけを隔離の根拠にはしない。

## 4. 起動と復元の規則

新規利用の標準の入口は Agent。既存利用者の前回状態と、明示的な起動操作を尊重する。
設定名・値は以下を設計案とし、まだ利用可能な設定として案内しない。

| 優先順位 | 起動条件 | 着地 |
|---|---|---|
| 1 | ファイル・会話などを明示して開いた | 指定された対象。直接編集するファイルは Editor |
| 2 | `start_mode = agent` / `editor` を指定 | 指定された表示 |
| 3 | `start_mode = restore`（既定案）で前回状態あり | 前回の表示と選択対象 |
| 4 | 復元対象がない | Agent の新しい会話 |

移行後、旧 Chat / Fleet の復元先は Agent とし、選択されていた会話・Task は維持する。
旧 Editor は Editor として復元する。Agent を毎回開きたい利用者は `start_mode = agent` を選べる。

Agent に入ったときの選択は、明示的に開いた対象を最優先とする。
それがなければ要対応、実際に稼働中の作業、前回の会話、新しい会話の順に着地を決める。
要対応が複数ある場合の順序は既存のキューに従う。復元された過去の状態だけで「実行中」とは判定しない。
表示後に発生した通知で、入力中の会話から勝手にフォーカスを奪わない。

起動・一覧表示だけで全エージェントや WebView を起こしたり、Task を作成したりしない。
開いていない会話のコストと、既存の自動停止の仕組みを維持する。

## 5. 成果物を中心に確認する

中心の作業を「頼む → 見る → 指摘する → 直る」に置く。
プレビュー可能な成果物がある制作ではプレビュー、コード変更の確認では変更レビューを優先する。
既に開閉を選んだペインはその選択を記憶し、毎ターン開き直さない。
ファイルツリー・ターミナル・ソースは、必要なときにすぐ開ける位置に置く。

成果物の帯を、再起動後も成果物へ戻れる安定した入口にする。
成果物から元の会話や作業先へ戻れ、ファイルの場所を確認・持ち出せるようにする。
バックエンドの変更など、プレビューでは判断できない作業には diff・テスト結果・検証内容を添える。

### AI 横断で維持するもの

成果物は普通のファイルとして保存し、表示と識別は特定の Agent に依存させない。
同じファイルを別の Agent に渡して修正し、同じ Viewer で確認できる体験を目指す。

ただし、ファイルを共有できることと、会話履歴・権限・実行中セッション・操作ツールを引き継げることは別。
現 Chat は Claude 固有のプリセットに依存しているため、他 Agent への対応は能力を確認して段階的に行う。
UI を統合しただけで全 Agent が同じ機能を使えるとは扱わない。

## 6. ブラウザは Viewer と操作先を分けて育てる

成果物の確認場所は内蔵 Viewer を標準とする。
既存の HTML 表示・localhost の Web タブ・Design Mode・Inspector を活用し、
会話の横で表示を確認し、要素を指して修正を頼める体験を磨く。

AI の自動検証は、まず既存ツールによる外部 Chrome 連携から試す。
その後、同じ画面を人間と AI で共有する価値と実装コストを確認し、内蔵 Viewer の直接操作を検討する。

| 用途 | 標準にする場所・方式 |
|---|---|
| HTML・図などを会話の横で見る、要素を指して修正する | 内蔵 Viewer / Design Mode |
| 実際の Chrome で画面遷移・フォーム・表示を検証する | 外部 Chrome と既存の自動操作ツール |
| ログイン済みの外部サービスを操作する | 利用者が選んだ外部ブラウザ連携 |
| AI と同じタブを内蔵画面で見ながら操作を進める | Viewer の直接操作を次段階で検証 |

### 外部 Chrome 連携

Claude の公式 Chrome 拡張は Claude Code と連携し、ログイン状態を使ったブラウザ操作ができる。
これは Claude 向けの連携として扱い、他 Agent も同じ拡張を利用できる前提にはしない。
AI 横断の接続候補には Playwright MCP 等がある。既存タブへの拡張接続も含め、
necoder の ACP 経由で使えるかは Agent ごとに通して確認する。
外部ツールの導入や常駐プロセスは、自動的に全利用者へ追加しない。

外部 Chrome と Viewer は別のブラウザである。同じ URL を開いても Cookie・入力内容・スクロール位置などは一致しない。
操作中のブラウザ・タブ・対象 URL を表示し、結果とスクリーンショットを会話へ戻す。
外部の操作対象タブを開く入口を用意し、Viewer の画面を検証結果として代用しない。
Fleet で並走するときは、Task ごとに操作対象とプロファイルを区別する。

### 内蔵 Viewer の操作口

`necoder mcp` から対象を指定して `open / snapshot / click / fill / console / screenshot` 等を呼ぶ案は残す。
MCP は操作を届ける方式であり、内蔵・外部のどちらを使うかとは独立した選択。
接続方式に加えて、同じタブを共有する価値と、各 Agent・OS での操作能力を評価する。

着手時には、次を含む小さな試作で成立性を確認する。

- 操作を対象の窓・Task・タブに結び付ける。表示中の別 Task へ流さない。
- ページ遷移後の古い要素参照、タブ消失、読み込み失敗・タイムアウトを区別して返す。
- クリック命令を送れたことと、期待した動作を確認できたことを区別する。
- Chat artifact の隔離と、開発サーバの操作可能範囲を分ける。汎用の特権 IPC を成果物へ開放しない。
- macOS の WKWebView と Windows の WebView2 は、それぞれ実機で検証する。
  外部 Chrome 拡張や Playwright が、そのまま既存の埋め込み WebView を制御できるとは扱わない。

まず localhost の開発ページを対象とし、任意のサイトを扱う汎用ブラウザへの拡張は別に判断する。

## 7. シミュレーターは既存の実行環境へ接続する

iOS / Android は、当面 Simulator.app や既存のエミュレーターで表示する。
necoder は利用者が選んだ MCP サーバ等の接続方法を案内し、操作結果やスクリーンショットを会話へ戻す流れを確認する。
ライブ映像の埋め込みや独自の操作基盤は、この計画に含めない。

[ORCA-PARITY](./ORCA-PARITY.md) §4 の F13 の調査を基準とする。
`simctl` の起動・撮影機能だけで任意の UI 操作まで完結すると見なさず、必要な補助ツールを接続先ごとに確認する。
モバイル開発者に内蔵表示が必要かを確かめ、価値が具体化した段階で再検討する。

## 8. 実装の順序と判断基準

1. **行き先と一覧の統合**: 既存 Chat のセッションを維持したまま、Agent 表示から相談とプロジェクトの会話へ入れるようにする。
2. **起動と復元**: 明示起動・設定・前回表示・要対応の優先順位を確定し、Editor とすぐ往復できるようにする。
3. **成果物の確認**: プレビューと変更レビューへの導線を優先し、ファイルツリーは必要時に開く。
4. **外部ブラウザでの自動検証**: 既存ツールを接続し、対象表示と結果の還流までを一周させる。
5. **内蔵 Viewer 操作の試作**: 外部連携で残った不便を基に、対象を限定して価値とコストを判断する。
6. **Chat モードの移行完了**: 履歴・成果物・設定の互換と復元を確認して、独立したモードの入口を畳む。

シミュレーターの接続案内は独立した小さな単位として進められる。
ブラウザの各段階が終わることを、Agent / Chat の画面統合の必須条件にはしない。

試用では、次の三つの作業を最後まで通す。

- プロジェクトなしで相談し、単体 HTML を作り、表示を見ながら同じファイルを修正する。
- 既存プロジェクトを変更し、プレビューまたは diff と検証結果を確認して、必要な部分を Editor で編集する。
- 対応を確認した別 Agent に同じ成果物を渡し、修正結果を同じ場所で確認する。

初回の成果物までの迷い、修正を完了できるか、作業先の取り違え、Editor が必要になる場面、
起動・入力・idle メモリを確認する。Editor の利用回数を減らすこと自体は成功指標にしない。
起動設定は目安二週間のドッグフーディングで比較し、必要なら利用者が明示的に有効にするローカルの最小限の記録を使う。
会話本文や資格情報を記録対象にせず、外部テレメトリは追加しない。

## 9. 参考情報と判断の限界

以下は 2026-10-27 に確認した外部の公式資料。製品仕様は変わり得る。

- [Cursor: Agents Window](https://cursor.com/docs/agent/agents-window) — Agent 中心の画面と Editor を併存させている。
- [Anthropic: Claude Cowork and chat come together for Enterprise](https://claude.com/resources/articles/unified-claude-enterprise)
  — 質問と作業の入口を統合する方向の事例。
- [Claude Code: Use Claude Code with Chrome](https://code.claude.com/docs/en/chrome)
  — 公式拡張の接続条件とブラウザを使った検証。
- [Microsoft: Playwright MCP](https://github.com/microsoft/playwright-mcp#user-profile)
  — 操作ツールの接続候補。既存ブラウザへの接続と、並列利用時のプロファイルの制約。

Agent 機能・製品全体の利用増加と、Agent 画面が Editor より選ばれている割合は別の指標。
今回確認した資料から画面別の利用比率は分からないため、「大多数が IDE を使わなくなった」ことを採用理由にはしない。
necoder の判断は、入口の分かりやすさと、成果物を作って検証・修正する作業を一続きにできるかを基準にする。
