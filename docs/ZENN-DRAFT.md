## はじめに

どうも、最近はAIモデルだけでなくコードエディタまで作り始めただいちです。

エディタでClaude Codeを使っているとき、ずっと気になっていたことがありました。

複数のプロジェクト、ブランチ、AIスレッドを並行していると、**今どこにいて、どのAIが何を触っているのか分からなくなる**んですよ。

欲しかったのは、プロジェクトやブランチごとの色が、タブ、キャレット、AIスレッドまで一貫して続くUIでした。ところが既存エディタの拡張機能では、この手のUI自体を追加できません。

じゃあ自分で作るか、となりました。

作ったのが、AIエージェント時代のコードエディタ **necoder（ねこーだー）** です。

## necoderとは

necoderは、RustとGPUIで作ったネイティブのコードエディタです。ElectronもWebViewも使っていません。

普通の編集機能に加えて、最初からAIエージェントを中核に置いています。

- Claude CodeなどのAIエージェントをACP経由で実行
- プロジェクト、ブランチ、スレッドを色で識別
- diffの承認・却下、チェックポイント、巻き戻し
- AIが自分で更新するTodoボード
- 複数worktreeとAIエージェントを並べるFleet画面
- LSP、tree-sitter、Git、統合ターミナル、Remote SSH
- 日本語・英語UI

Claude Codeは手元のCLIを起動するので、既存のサブスクリプションをそのまま使えます。別のAPIキーをnecoderに登録する必要はありません。

## 使った技術

主要な構成はこんな感じです。

| 領域 | 技術 | 役割 |
|---|---|---|
| UI | Rust + GPUI | ネイティブUIとGPU描画 |
| 編集コア | ropey | 大きなテキストを扱うrope |
| シンタックス | tree-sitter | Rust、TypeScript、Python、Goなどの増分解析 |
| 言語機能 | LSP | 補完、診断、定義ジャンプ、rename、code action |
| AI | Agent Client Protocol（ACP） | Claude Codeなどとの共通接続 |
| ターミナル | alacritty_terminal | PTYと端末エミュレーション |
| 永続化 | Turso | hot exit、スレッド、チェックポイントのメタデータ |
| Git | Git CLI + imara-diff | worktree、blame、hunk操作、gutter diff |
| Remote SSH | OpenSSH + Rust製remote server | 手元と同じUIでリモート編集 |

エディタコアはGPUIを知らない純Rustのcrateに分離しています。AI、Git、ターミナルも編集コアには入れません。

## こだわり1：色を「装飾」ではなく「住所」にした

necoderで一番やりたかったのはこれです。

プロジェクトやブランチに識別色を持たせ、その色を左のレール、タブの下線、キャレット、AIスレッド、diffの行き先まで通しています。

色を増やせば分かりやすくなるわけではありません。エラー、実行中、承認待ちまで別の色を使い始めると、今度は何の色なのか分からなくなります。

なのでnecoderでは、**色は場所とスレッドの識別だけ**に使います。状態は形と動きで表す。このルールはかなり厳しく守っています。

自分は、エディタのタブはファイルを並べるためだけのものではなく、今いる場所を見失わないためのものだと思っています。その考えをプロジェクトとAIスレッドまで広げました。

## こだわり2：AIチャットを「横に置いた機能」で終わらせない

多くのエディタのAI機能は、右側にチャット欄を追加した形です。

necoderでは、AIスレッドもプロジェクトやworktreeと同じ単位で扱います。

たとえばFleetでは、タスクを作るとbranch、linked worktree、プロジェクトセッション、AIパネルが一緒に作られます。複数のAIを別worktreeで走らせ、進行中、承認待ち、完了を1画面で確認できます。

また、AIがファイルを変更するとdiffを出し、人間が承認・却下できます。ターンごとのチェックポイントも保存するので、「さっきの状態に戻して」もGit commitなしで行えます。

チャットの履歴を見せるだけではなく、**AIがどこで何をしていて、人間が次に何を判断すべきか**までUIに持たせました。

## こだわり3：速さのためにGPUIを選んだ

最初はTauriも検討しました。自分はTauri v2でデスクトップアプリを作ったことがあり、Web技術でUIを組める楽さも知っています。

ただ、今回はコードエディタです。1日中触るものなので、入力と描画の気持ちよさは妥協したくありませんでした。

そこでZedと同じGPUIを選びました。開発時の計測では、macOSでcold startが約215ms、アイドル時のRSSが約122MBです。1.6MBのファイルを開いても可視行だけをshapeするため、アイドルCPUは0%でした。

もちろんGPUIは楽ではありません。

- crates.ioの安定版ではなく、Zedのgit revisionを固定して使う
- ドキュメントが薄く、実際にはソースを読む場面が多い
- API変更の影響をそのまま受ける
- macOS、Windowsで描画やウィンドウ周りの罠が違う

かなり早期採用者向けです。それでも今回は、WebViewを挟まないこと自体がプロダクトの一部だったので採用しました。

## こだわり4：フォントもアプリに埋め込んだ

そう、HackGenではありません。

コード用に採用したのは **Guguru Sans Code** です。Google Sans Codeのラテン文字とIBM Plex Sans JPの日本語を組み合わせた等幅フォントです。

UIには **IBM Plex Sans JP**、コードには **Guguru Sans Code** を使っています。つまりUIとコードで日本語部分の血統が揃います。画面全体の雰囲気が分断されず、日本語コメントも2セル幅で綺麗に揃います。

RegularとBoldを含む4ファイルを`include_bytes!`でバイナリに埋め込み、起動時にGPUIのtext systemへ登録しています。合計約15MB増えますが、ユーザーの環境によって見た目や文字幅が変わるより良いと判断しました。どちらもSIL Open Font License 1.1です。

ちなみに実装初期、文字幅の計算は合っているのに画面には文字が1文字も出ない、という事故がありました。

原因はmacOS側の`font-kit` featureが無効だったことです。shapeはできる。しかしグリフをラスタライズできない。背景やキャレットだけ出て、文字だけ完全に透明でした。

エディタを自作すると、フォントは設定項目ではなく描画エンジンの一部なんだとよく分かります。

## 開発はdocsを先に書いた

necoderはCoding Agentと一緒に作っています。

ただし、毎回チャットで設計を説明するやり方にはしていません。リポジトリの`docs/`に、次の文書を置いています。

- `ROADMAP.md`: マイルストーンと受入条件
- `ARCHITECTURE.md`: crate境界と依存方向
- `UI-SPEC.md`: 色、余白、操作のルール
- `DECISIONS.md`: なぜその選択をしたか
- `JOURNAL.md`: 実装結果、失敗、次にやること

コードより先に受入条件と境界を更新し、Agentはそこを読んで実装します。

特に効いたのはJOURNALです。「何を実装したか」だけでなく、「何を疑って外したか」「次に同じ症状が出たらどこを見るか」まで残しています。少なくとも自分の開発では、成功ログより失敗ログの方が役に立ちました。

2026年7月中旬の最初のcommitから約6週間。現在はテストを含めてRust約6.5万行、23個のcrateになりました。ちなみに本家Zedは240以上のcrate、Rust150万行超という巨大さです。あの規模でも破綻しないのはcrate分割と依存方向の規律のおかげで、necoderも最初から同じ流儀に倣っています。エディタがperson-decades級と言われる理由はだいぶ分かりました。

## 既存エディタをforkしなかった理由

「Zedをforkした方が早くない？」とは当然思いました。短期的にはその通りです。

ただ、今回変えたかったのはUIの表層ではなく、プロジェクト、worktree、AIスレッドという単位そのものです。猛烈な速度で開発される本家に対して永遠にrebaseし続ける未来も見えたので、アプリケーションコードはforkせず、GPUIと公開仕様、外部ライブラリの上にnecoder固有の実装を載せています。ソースはAGPL-3.0-or-laterで公開しています。

## まとめ

necoderで特にこだわったのは、この4点です。

1. 色を装飾ではなく、プロジェクト・ブランチ・スレッドの住所にする
2. AIをチャット欄ではなく、worktreeと並ぶ作業主体として扱う
3. Rust + GPUIでネイティブの速さを取る
4. IBM Plex Sans JPとGuguru Sans Codeを埋め込み、文字の見え方まで揃える

まだ作りたいものは大量にあります。ただ、自分が欲しかった「複数のプロジェクトとAIを並行しても迷わないエディタ」は、かなり形になってきました。
