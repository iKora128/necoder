## 1. 記録と完了の規律

- 項目IDは維持し、同じ問題は既存項目に追記する。解消しても消さず、修正コミットと検証を残す。
- 状態は **要対応 / 要検証 / 作業中 / 修正実装あり・検証待ち / 検証済み解消** で区別する。
- 根拠は、対象worktree・コミットまたは未コミット差分・ファイル・関数まで記す。行番号だけに依存しない。
- **コードで確認した構造**と、**そこから推定した影響**と、**実機再現した事実**を分ける。
- 受入条件のチェックは実際に確認してから入れる。「関数がある」「単体テストが通る」だけで操作全体の完成とはしない。
- 作業中のブランチは更新される。着手前に最新実装で再判定し、過去の指摘を機械的に再実装しない。
- 新しい項目には、優先度・状態・対象版・根拠・利用者への影響・改善案・確認条件を付ける。

## 4. 詳細と確認条件

### R01 — レビュー情報とコードの版

- **対象/根拠**: review `dddca59`、統合 `8277d4f`。`crates/review_view/src/review_view.rs` の
  `reviewed: HashSet<String>`、`apply_diff`、`select_base`、`rebuild_rows_at`。
  `notes.rs::DiffLinesTarget` はbaseと抜粋を保存するが、行への配置はpath/side/行番号を使う。
- **確認した構造**: 再読込でレビュー済み集合を消さない。配置時に注記のbaseや抜粋の一致を確認しない。
- **影響**: 確認後に内容が変わってもレビュー済みのまま。行挿入や比較基準変更で別のコードに注記が付く可能性。
- **改善案**: 確認済みの内容ハッシュを保持。注記は対象版を記録し、再配置に確信がなければ「位置が変わった注記」として分離。
- [ ] レビュー済みファイルをエージェントが更新すると、確認が必要になったと分かる。
- [ ] 注記の前に行を挿入、rename、比較baseを変更しても、無関係な行に黙って付かない。
- [ ] 再配置できない注記も元の抜粋とともに閲覧・再送できる。

### R02 — レビューのメモリ・解析予算

- **対象/根拠**: 統合 `8277d4f`。`crates/project/src/review.rs::review_diff_on` / `git_diff_patch_on` /
  `review_file_texts_on`、`crates/review_view/src/review_view.rs::reload` / `load_syntax`、`syntax.rs::HighlightedText`。
- **確認した構造**: trackedの事前制限は変更行数中心。全体60,000行のbudgetはuntrackedループでは減らない。
  全変更ファイルの旧・新全文を順次読んでハイライトを保持し、各chunkの反映で行全体を再構成する。
  `MAX_TEXT_BYTES` は全文ハイライト等にはあるが、trackedパッチ取得全体のバイト上限ではない。
- **影響（未計測）**: 数MBの1行、上限内ファイルの大量追加、巨大リポジトリの一括整形でメモリ/解析量が増大する。
  可視行の仮想化だけでは読込・保持・解析量を抑えられない。
- **改善案**: tracked/untracked共通のバイト・行・件数予算、出力取得時の上限、可視周辺からの解析、キャッシュ回収。
  全行の再構成は差分更新またはまとめた更新にする。
- [ ] 数MBの1行変更でもパッチ取得・解析の上限が働く。
- [ ] 追跡外ファイルの合計が60,000行を越えるケースを、全体予算として扱う。
- [ ] 多数の約1MBファイルを変更しても、非表示全文の保持でRSSが際限なく増えない。
- [ ] 読込中にbaseを変更/画面を閉じた際、不要になった処理量も減る（結果を捨てるだけと区別）。

### R03 — 注記の保存順序と失敗表示

- **対象/根拠**: review `dddca59`。`annotations.rs::persist_note` / `delete_note` / `mark_notes_sent`、
  `crates/storage/src/storage.rs::upsert_review_note` / `delete_review_note`。
- **確認した構造**: 更新と削除を独立したbackground taskとしてdetach。upsertは更新世代にかかわらず上書き。
  エラーは `eprintln!` のみ。DBの直列化だけではbackground taskの到着順を保証しない。
- **影響（競合再現は未）**: 古い本文・未解決状態への巻戻り、削除後の復活、保存できないのに保存済みと見える。
- **改善案**: 注記単位の順序制御、単調なrevisionと削除記録、保存結果のUI反映。必要なら再試行を可能にする。
- [ ] 保存を遅延させたまま編集→解決→削除しても、再起動後に復活しない。
- [ ] 更新を逆順で到着させても最新revisionが残る。
- [ ] DB失敗が利用者に分かり、本文を失わず再試行できる。

### R04 — 複数窓で実行中の窓を閉じる

- **対象/根拠**: keeprun `8ebaa5c`（文書化時の `5dbf8f0` でも該当分岐を確認）。
  `crates/workspace/src/workspace/quit_guard.rs::guard_window_close` の `if other_windows { return false; }`。
- **確認した構造**: 別のWorkspace窓があれば、この窓の実行状況を調べずcloseを許可。
- **影響**: A窓で実行中、B窓が開いているとA窓を確認なしで閉じられる。窓所有の実行を失う経路。
- **改善案**: 最後の窓かどうかと、この窓の仕事が止まるかどうかを分離。
- [ ] AでWorking/Blocked/実行中PTY、Bでidleの状態で、Aを閉じる時にも保護が働く。
- [ ] Bだけを閉じる時は不要な確認をしない。
- [ ] ⌘Q、窓の×、端末タブの×の対象範囲と説明が一致する。

### R05 — Design Modeの非同期添付先

- **対象/根拠**: 統合 `8277d4f`。`workspace/web_preview_view.rs::capture_pick` / `finish_pick`、
  `workspace/web_tabs.rs::on_web_preview_event` / `panel_for_web_view`。
- **確認した構造**: 撮影完了後にsessionの現在のagent_panelを引いてcomposerへ追加する。
  完了結果には選択時のスレッドID・ページ世代を照合する情報がない。
- **影響（実機再現は未）**: 撮影中にスレッドを変えると別会話へ添付。キャンセル/再読込後に古い結果が添付され、
  フォーカスが移ったり、新しいDesignセッションを終了させたりする余地。
- **改善案**: 選択時のTask/パネル/スレッドIDとDesign・navigationの世代を固定し、完了時に照合する。
- [ ] 撮影を遅延してスレッド/Taskを切り替えても、別の宛先へ添付されない。
- [ ] キャンセル→Design再開、再読込、タブclose後の古い結果で新しい操作を壊さない。
- [ ] 複数選択の撮影完了順が逆転しても、要素・画像・説明の組と利用者の意図した順序を保つ。

### R06 — URLの実行ホスト

- **対象/根拠**: 統合 `8277d4f`。`workspace/web_tabs.rs::open_url(&str, ...)` と端末URLの共通入口。
- **確認した構造**: localhost判定はURL文字列で、実行ホストを受け取らずローカルWebViewへ渡す。
- **影響**: SSH先のlocalhost URLを手元で開く。同じポートで手元の別アプリが動いていると成果を取り違える。
- **改善案**: URLと発生元のHostId/Taskを運ぶ。転送未対応時も手元のlocalhostへ黙って置換せず、理由と操作を示す。
- [ ] 手元/SSH先の同じポートに別ページを用意して、正しいホストのページが開くか、明示的な案内になる。
- [ ] SSH再接続・Task切替後もポート転送とプレビューの帰属がずれない。

### R07 — 注記の送信先の識別子

- **対象/根拠**: review `dddca59`。`review_view.rs::SendTarget` のpanel/thread添字、
  `workspace/review_controller.rs::review_send_targets` / `send_review_notes`。
- **確認した構造**: メニュー生成時の添字を、選択時にそのまま参照する。
- **影響（再現は未）**: メニュー表示中のスレッドclose/並替えなどで、表示名と送信先が食い違い得る。
- **改善案**: Task・Entity・スレッドの安定IDで指定し、送信直前に存在を確かめる。消えた宛先への送信は失敗として残す。
- [ ] メニュー表示後に宛先より前のスレッドをclose/並替えしても、元の対象に届く。
- [ ] 宛先を削除した場合は注記を送信済みにせず、別宛先を選び直せる。

### R08 — 使用量とアカウントの識別

- **対象/根拠**: usage `ec6781b`、文書化時の `12835bb` でも `agent_panel/usage.rs::UsageLimits` は
  `BTreeMap<SharedString, AgentLimits>`（エージェント名）で共有。
- **影響**: 同じエージェントでもSSH先/手元、認証環境、アカウントが異なる場合に同じ値として見せる余地。
- **改善案**: provider・実行host・認証profileを区別。取得時刻と不明/古い値も示す。アカウント切替時には古い値を失効させる。
- **訂正**: 初回の「Codexの取得関数に呼出元がない」は、`12835bb` の `workspace/usage_view.rs` で接続済み。
  UI未接続を現在の欠陥として残さない。更新後の画面操作は今回未検証。
- [ ] 同じproviderで異なる認証環境の2スレッドを動かし、値が混ざらない。
- [ ] 認証切替・取得失敗・reset時刻通過後に、古い値を新しい値として見せない。
- [ ] エージェントが報告しない使用量を0と断定しない。推定額と実際の請求額を区別する。

### R09 — Captainの承認からTask作成までの復旧

- **対象/根拠**: main `97e8666` + 2026-09-26未コミット変更。
  `workspace/captain_proposals.rs::approve_captain_proposal` / `resolve_proposal` / `create_proposed_tasks`、
  `storage.rs::resolve_captain_proposal` / `load_pending_captain_proposals`。
- **確認した構造**: カード除去→承認をDBへ確定→Task作成。DB失敗時はトーストだけでカードを戻さない。
  起動時復元はpending案で、承認済み案の未作成行を再開する実行記録が見当たらない。
- **影響**: 承認後に終了するとTaskが作られない、一部作成後の残りを再試行しにくい。
- **改善案**: 承認と実行完了を分け、提案ID+行IDごとに待機/作成中/成功/失敗を永続化。
  DBとgitを一つのトランザクションにできる前提を置かず、再実行で重複しない復旧手順を持つ。
- [ ] 承認保存直後・worktree作成直後・担当起動直前に終了させても、安全に再開できる。
- [ ] 3行中1行だけ失敗した際、成功済みのTaskを重複作成せず残りを再試行できる。
- [ ] DB失敗後も案と選択内容が残る。

## 5. 良い設計として維持したい点

- ReviewViewは独立crateで、AIへの送信はWorkspaceが担う。レビュー行はモデルへの添字で本文を複製しない。
- レビュー読込結果の世代照合、表示の仮想化、単一ファイル等の制限は既にある。R02はこれらを否定せず全体予算を補うもの。
- 任意スレッドへの送信とキュー進行が、表示を奪わず行えるようになった。
- Design Modeはサイズ・形式・nonceを検査し、送信文の秘密らしい値を伏せる。WebViewの回収設定も利用している。
- Skillsの探索/導入基盤はGPUI非依存。使用量取得は画面操作をきっかけとし、定期ポーリングを増やしていない。

## 6. 次回の追記対象

文書化中に増えた機能は未レビューのまま完了扱いにしない。次の追記では対象コミットを固定する。

- Explorer: 並替え・仮想化・ドラッグ中の対象・ignored-files検索と大量ファイル時の上限。
