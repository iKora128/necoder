## 1. 記録と完了の規律

- 項目IDは維持し、同じ問題は既存項目に追記する。解消しても消さず、修正コミットと検証を残す。
- 状態は **要対応 / 要検証 / 作業中 / 修正実装あり・検証待ち / 検証済み解消** で区別する。
- 根拠は、対象worktree・コミットまたは未コミット差分・ファイル・関数まで記す。行番号だけに依存しない。
- **コードで確認した構造**と、**そこから推定した影響**と、**実機再現した事実**を分ける。
- 受入条件のチェックは実際に確認してから入れる。「関数がある」「単体テストが通る」だけで操作全体の完成とはしない。
- 作業中のブランチは更新される。着手前に最新実装で再判定し、過去の指摘を機械的に再実装しない。
- 新しい項目には、優先度・状態・対象版・根拠・利用者への影響・改善案・確認条件を付ける。

## 4. 詳細と確認条件

### R01 — レビュー情報とコードの版

- **対象/根拠**: review `dddca59`、統合 `8277d4f`。`crates/review_view/src/review_view.rs` の
  `reviewed: HashSet<String>`、`apply_diff`、`select_base`、`rebuild_rows_at`。
  `notes.rs::DiffLinesTarget` はbaseと抜粋を保存するが、行への配置はpath/side/行番号を使う。
- **確認した構造**: 再読込でレビュー済み集合を消さない。配置時に注記のbaseや抜粋の一致を確認しない。
- **影響**: 確認後に内容が変わってもレビュー済みのまま。行挿入や比較基準変更で別のコードに注記が付く可能性。
- **改善案**: 確認済みの内容ハッシュを保持。注記は対象版を記録し、再配置に確信がなければ「位置が変わった注記」として分離。
- [ ] レビュー済みファイルをエージェントが更新すると、確認が必要になったと分かる。
- [ ] 注記の前に行を挿入、rename、比較baseを変更しても、無関係な行に黙って付かない。
- [ ] 再配置できない注記も元の抜粋とともに閲覧・再送できる。

- **対応（2026-09-26・`23eaa57`）**: 見た印を「見た時の比較の基準 + ファイルの差分の指紋」に結び付け、同じ基準で差分が変わったら印を外して畳みを開き「見た後に変更あり」。注記は置く前に抜粋と今の行を突き合わせ（`positions::locate`）、合わなければ同じ中身の 1 か所へ移すか「位置が変わった注記」として見出しの直後に元の抜粋つきで出す（プロンプトにも印）。
  - 検証: `locate` の単体 6 件、実 repo で「上に 2 行挿入 → 注記は 7 行目へ・見た印が外れる」「書き換え → 見出しの直後」。改名の追従はコードのみ（テスト無し）。実画面は未。

### R02 — レビューのメモリ・解析予算

- **対象/根拠**: 統合 `8277d4f`。`crates/project/src/review.rs::review_diff_on` / `git_diff_patch_on` /
  `review_file_texts_on`、`crates/review_view/src/review_view.rs::reload` / `load_syntax`、`syntax.rs::HighlightedText`。
- **確認した構造**: trackedの事前制限は変更行数中心。全体60,000行のbudgetはuntrackedループでは減らない。
  全変更ファイルの旧・新全文を順次読んでハイライトを保持し、各chunkの反映で行全体を再構成する。
  `MAX_TEXT_BYTES` は全文ハイライト等にはあるが、trackedパッチ取得全体のバイト上限ではない。
- **影響（未計測）**: 数MBの1行、上限内ファイルの大量追加、巨大リポジトリの一括整形でメモリ/解析量が増大する。
  可視行の仮想化だけでは読込・保持・解析量を抑えられない。
- **改善案**: tracked/untracked共通のバイト・行・件数予算、出力取得時の上限、可視周辺からの解析、キャッシュ回収。
  全行の再構成は差分更新またはまとめた更新にする。
- [ ] 数MBの1行変更でもパッチ取得・解析の上限が働く。
- [ ] 追跡外ファイルの合計が60,000行を越えるケースを、全体予算として扱う。
- [ ] 多数の約1MBファイルを変更しても、非表示全文の保持でRSSが際限なく増えない。
- [ ] 読込中にbaseを変更/画面を閉じた際、不要になった処理量も減る（結果を捨てるだけと区別）。

- **対応（2026-09-26・`dc11009`）**: パッチを取る前に 4MB 超を除く（`git ls-tree -l` 1 回 + 作業ツリーの大きさ）。パッチ後に 1 ファイル 512KB・全体 16MB のバイト上限。追跡外も残りの行・バイトの予算の中で読む。全文は全体 24MB まで。全文到着ごとの行の並べ直しを 120ms に 1 回へ。
  - 検証: 小さい上限（`ReviewBudgets`）で 1 行 64KB の変更・300KB のファイル・予算切れの追跡外・全文の予算をテスト。RSS の実測は未（R14 と一緒に測る）。git 2.43 の `core.bigFileThreshold` は diff を止めないことを確かめたので使っていない。
- **対応の追補（2026-09-27・読み込みの取り消し）**: 4 つ目の確認条件。予算（上の対応・#30 の版）は変えず、別の土台の版（`d122ecf`）から取り消しの考え方だけを移した。1 回の読み込みごとに取り消しの印（`project::review::ReviewCancel`）を作り、基準の変更・読み直し（`空白を無視` の切替を含む）・変更レビューのタブを閉じる（レール / ブランチの切替でタブ列ごと消えた時も）・ビューの破棄（session を閉じた）で立てる。背景は区切りで印を見て、残りを読まずに抜ける（git の呼び出しの間・作業ツリーの大きさの確認 1 件ごと・追跡外 1 件ごと・全文 1 件ごととハイライトの前）。手元の git は走っている途中でも子を止める（`Host::run_command_cancellable`・読み取り専用の `--no-optional-locks` の git だけに使う）。差分の途中で閉じたら次に開いた時に読み直し、全文の途中なら読み終えていないファイルから続きを読む（全文 24MB の予算も続きから数える）。Fleet の Task カードで「変更」タブを選んだままなら、エディタのタブを閉じても止めない（Fleet へ戻ると読み込みの入口を通らずにそのまま見えるため）。
  - 検証: 呼び出しを数える host で、取り消さなければ追跡外 20 件を全部読み、3 件目で取り消すとそこで止まる／`--name-status` の最中に取り消すと残りの git を頼まない／旧側の `git show` の最中に取り消すと新側を読まない／始める前の取り消しは git も叩かない。ビューでは、読み込み中に基準の変更と読み直しを続けると git と読み込みは最後の 1 回分だけ／閉じると 0 件で、次に表示した時に読み直す／ビューを捨てても 0 件／全文を 3 件目で取り消すと残りを読まず、また表示すると 3 件目から続きを読む。タブの ×・タブ列の入れ替え・Fleet の場合分けは workspace のテスト。**取り消しを効かなくした変異でこれらのテストが落ちる**（結果を捨てるだけの実装と区別できている）ことも確かめた。手元の子を止める経路は `exec sleep 30` を 100ms で取り消してすぐ戻ること。隔離 offscreen の実画面（REVIEW_PROBE に `close` / `reload` / 読み込みの様子を出す `state` を足した）で、60 ファイル・129MB の repo を開いて 250ms で閉じると、`git diff --numstat`（閉じなければ約 0.5〜0.6 秒）が約 0.18 秒で子ごと消え、続くパッチの git は走らなかった（子プロセスを 20ms ごとに見て確かめた）。読み込み中に基準を変えると、前の基準の numstat が同じく消えて新しい基準の numstat に替わった。400 ファイルの repo で全文の途中（閉じた時点で 24/400）で閉じると 4.5 秒たっても 24 のまま、開き直すと 48 まで進んだ（0 からではなく続きから）。どの場合も最後の画面は崩れず、新しい基準の中身だけが出た。
  - 未検証: SSH 実機（1 往復の途中では止まらず、その 1 回は最後まで走ってから抜ける想定）・Windows 実機（子を止める経路）・大きな repo での CPU 時間と RSS の実測（R14 と一緒に測る）。Fleet の「変更」タブから別のタブへ移っただけでは止めない（閉じる操作ではないため）。

### R03 — 注記の保存順序と失敗表示

- **対象/根拠**: review `dddca59`。`annotations.rs::persist_note` / `delete_note` / `mark_notes_sent`、
  `crates/storage/src/storage.rs::upsert_review_note` / `delete_review_note`。
- **確認した構造**: 更新と削除を独立したbackground taskとしてdetach。upsertは更新世代にかかわらず上書き。
  エラーは `eprintln!` のみ。DBの直列化だけではbackground taskの到着順を保証しない。
- **影響（競合再現は未）**: 古い本文・未解決状態への巻戻り、削除後の復活、保存できないのに保存済みと見える。
- **改善案**: 注記単位の順序制御、単調なrevisionと削除記録、保存結果のUI反映。必要なら再試行を可能にする。
- [ ] 保存を遅延させたまま編集→解決→削除しても、再起動後に復活しない。
- [ ] 更新を逆順で到着させても最新revisionが残る。
- [ ] DB失敗が利用者に分かり、本文を失わず再試行できる。

- **対応（2026-09-26・`9e182e2`）**: 書き込みをビューごとの 1 本の列で積んだ順に流す。storage の upsert は `updated_at` が古い書き込みを捨てる。失敗はトレイに「⚠ 保存できていない変更 N 件」+ 再試行（消した注記は書き戻さない）。読み込みが遅れて届いても消した注記を戻さない。
  - 検証: 編集→解決→削除を 20 シードで回し復活しない（**旧実装では seed 0 で復活して落ちることを確認**）、逆順の upsert、再試行。DB 失敗の実機再現は未（失敗は関数を直接呼んで確かめた）。

### R04 — 複数窓で実行中の窓を閉じる

- **対象/根拠**: keeprun `8ebaa5c`（文書化時の `5dbf8f0` でも該当分岐を確認）。
  `crates/workspace/src/workspace/quit_guard.rs::guard_window_close` の `if other_windows { return false; }`。
- **確認した構造**: 別のWorkspace窓があれば、この窓の実行状況を調べずcloseを許可。
- **影響**: A窓で実行中、B窓が開いているとA窓を確認なしで閉じられる。窓所有の実行を失う経路。
- **改善案**: 最後の窓かどうかと、この窓の仕事が止まるかどうかを分離。

## 5. 良い設計として維持したい点

- ReviewViewは独立crateで、AIへの送信はWorkspaceが担う。レビュー行はモデルへの添字で本文を複製しない。

- Design Modeはサイズ・形式・nonceを検査し、送信文の秘密らしい値を伏せる。WebViewの回収設定も利用している。
- Skillsの探索/導入基盤はGPUI非依存。使用量取得は画面操作をきっかけとし、定期ポーリングを増やしていない。

## 6. 次回の追記対象

文書化中に増えた機能は未レビューのまま完了扱いにしない。次の追記では対象コミットを固定する。
