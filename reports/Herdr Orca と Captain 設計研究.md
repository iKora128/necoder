# Herdr と Orca が空けた席に Captain が座る

Captain の骨格は変えなくていい。コードを書かない単一リード、台帳に置く状態、イベント駆動の wake、`necoder fleet` だけの采配、承認は推薦まで、統合は人間、という組み合わせは、製品各社と研究が 2026 年までに着いた場所と一致していた。Herdr（Rust 製の端末マルチプレクサ、Apache-2.0）と Orca（Electron 製の ADE、MIT）は、左に状態つきの一覧、中央に選んだ 1 本、という同じ型の上にいて、Herdr は端末を、Orca は worktree を管理の主語にする。采配役については Herdr が core に入れないと決め、Orca は実験的な層を持ちながら idle の coordinator を起こす方法を 4 か月解けていない。どちらも PTY 越しにエージェントを扱うのが原因で、台帳イベントを ACP のターンとして渡せる necoder はこの問題を最初から持たない。直すのは理念と実装のずれ 3 か所で、Captain スレッドが同名のまま再利用されてコンテキストが増え続ける、未配達の wake がプロセスメモリにある、書かない規律がプロンプト頼み、の 3 つ。足すのは委任文の型、完了報告の契約、別コンテキストの検証 Task、necoder 側で強制する上限、分解案の事前承認、stall の wake。避けるのは自律マージ、worker 同士の自由な連絡、LLM による見回りだ。ゲームの類推は、次の要対応へ 1 キー、動かない番号、1 体 1 タイルといった仕掛けを借りる範囲なら良い案で、世界観や絵を着せると Gas Town が払った翻訳の手間と常時描画のコストを招く。編隊図についての作者の直感は半分当たっている。概観の面は要るが、ハブ表示は星型で所属しか語らないので、図をゲームらしくするよりノードを情報タイルにして Captain の発令と待ちを見せた方が、開いておく理由のある画面になる。

## Herdr は端末を、Orca は worktree を主語にし、采配役の席はどちらも空いている

### Herdr は采配を core に入れないと決めた

Herdr は Can Celik（GitHub では ogulcancelik）がほぼ 1 人で書いている Rust 製の TUI で、リポジトリの説明文は "the runtime your coding agents live on"。2026-03-27 の v0.1.0 から半年で v0.9.1 まで進み、2026-09-20 時点で **star は 39,703**、Homebrew 経由の導入は直近 90 日で 48,476 件ある ([GitHub API](https://api.github.com/repos/herdrdev/herdr), [formulae.brew.sh](https://formulae.brew.sh/api/formula/herdr.json))。ライセンスは **2026-07-22 に AGPL-3.0-or-later から Apache-2.0 へ変わった**。7 月以前の紹介記事は AGPL と書いたままなので、古い比較を読むときは日付を見た方がいい ([CHANGELOG](https://github.com/herdrdev/herdr/blob/master/CHANGELOG.md), [#1340](https://github.com/herdrdev/herdr/issues/1340))。その後は org への移管、Y Combinator F26 入り、Bessemer 主導の $6M seed と続いた。作者ブログによれば商用の軸は laptop や VPS や sandbox に散らばった機械をつなぐ方向で、オーケストレーションを売る話は出てこない。ブログ 2 本は要約経由で読んだ情報なので、文言までは照合できていない ([YC 参加の告知](https://herdr.dev/blog/herdr-is-joining-y-combinator/), [seed の告知](https://herdr.dev/blog/herdr-raised-a-seed/))。人間のコミットは作者の 1,251 件に対して次点が 89 件で、採用が進むまで bus factor は実質 1 だ ([contributors](https://github.com/herdrdev/herdr/graphs/contributors))。

概念は session、workspace（UI 上の呼び名は Space）、tab、pane、agent の順に入れ子になっていて、pane は本物の端末、agent は pane の中で検出されたプロセスを指す ([concepts.mdx](https://github.com/herdrdev/herdr/blob/master/docs/versions/0.9.1/website/src/content/docs/concepts.mdx))。状態は blocked、working、done、idle、unknown の 5 値に見えるが、内部は 4 値と pane ごとの既読 1 bit で、done は idle かつ未読から導出している。サイドバーの rollup と並び順は同じ優先度関数（Blocked 4、未読の Idle 3、Working 2、既読の Idle 1、Unknown 0）を共有する ([aggregate.rs](https://github.com/herdrdev/herdr/blob/master/src/workspace/aggregate.rs))。necoder の ThreadActivity と同じ形で、ここは Herdr が正しい。

検出は苦しい。Herdr は 2026-04 に hook による状態報告を入れ、**2026-06-03 の 0.6.7 で Claude Code と Codex について撤退した**。いま hook が運ぶのは session ID だけで、状態は画面下部を TOML の manifest で読むスクレイピングが決める ([CHANGELOG](https://github.com/herdrdev/herdr/blob/master/CHANGELOG.md), [agents.mdx](https://github.com/herdrdev/herdr/blob/master/docs/versions/0.9.1/website/src/content/docs/agents.mdx))。docs は理由を、hook が "can miss permission approval results, escape interrupts, or other transitions" だからと説明している。`claude.toml` には "Braille covers <= 2.1.227; half-circles are the 2.1.228 busy spinner" というコメントがあり、Claude Code の版が上がるたびにスピナーの字形を追いかけているのが分かる ([claude.toml](https://github.com/herdrdev/herdr/blob/master/distribution/agent-detection/claude.toml))。blocked の判定はわざと厳しめで、知らない形のプロンプトは idle に落ちる。入力欄のゴースト提案文で idle 判定が外れる、Codex 0.154.0 で稼働中が idle になる、といった誤検出の issue が 2026-09 時点でも並ぶ ([#2959](https://github.com/herdrdev/herdr/issues/2959), [#4092](https://github.com/herdrdev/herdr/issues/4092))。ACP の permission request と stop reason を権威にできる necoder は、この追いかけっこに加わらなくて済む。

自動化の面は広い。CLI と socket API は同じ表面で、エージェント自身が pane を割り、別のエージェントを起動し、prompt を送り、状態を待てる ([agent-automation.mdx](https://github.com/herdrdev/herdr/blob/master/docs/versions/0.9.1/website/src/content/docs/agent-automation.mdx))。ところが 277KB の API schema を grep しても task、queue、depend、permission、origin、audit はどれも 0 回で、あるのはプリミティブだけだった ([herdr-api.schema.json](https://github.com/herdrdev/herdr/blob/master/docs/next/api/herdr-api.schema.json))。Kanban の要望に作者は "i dont want to bring big specialized features like this to main herdr" と答えて閉じている ([#301](https://github.com/herdrdev/herdr/issues/301))。

Herdr の上に采配役を自作した利用者の報告を並べると、Captain が先回りで塞いだ穴の一覧になる。最大 7 体の並走でポーリングが切れ、blocked を長時間見逃した事故が 3 回あった ([#4027](https://github.com/herdrdev/herdr/issues/4027))。`agent wait` の対象は 1 体だけなので、N 体なら最悪 (N−1) × timeout の遅れが乗る ([#4216](https://github.com/herdrdev/herdr/issues/4216))。別のエージェントが送った prompt を、受け手の Claude Code は transcript に human 由来と記録し、報告者は "the receiver asserts a human origin that is false" と書いた ([discussion #3584](https://github.com/herdrdev/herdr/discussions/3584))。購読イベントは約 500 件の滞留で黙って落ち、欠落の通知もない ([#4178](https://github.com/herdrdev/herdr/issues/4178))。コミュニティ製の Herdr Supervisor の作者は動機をこう書いている。"terminal state tells me whether a worker is busy or idle, but it does not tell me whether the outcome I wanted is actually complete." ([discussion #3607](https://github.com/herdrdev/herdr/discussions/3607))。端末の lifecycle と目的の達成は別物で、necoder が TaskPhase と ThreadActivity を別の enum に保っている理由がそのまま書いてある。こうした要望は 4 件とも not planned で閉じられた。判定したのはトリアージ bot で作者本人の却下ではないが、core を痩せたまま保つという発言、Kanban の却下、商用の軸がマシン接続にあることを合わせると、task や依存や承認 gate が Herdr の core に入る見込みは低い。

### Orca は采配の層を持つが、idle の coordinator を起こせていない

ORCA という名前は AI エージェント界隈に少なくとも 8 つある。作者の言う ORCA は stablyai/orca で確定してよく、Stably AI（YC W22）が MIT で出している ADE だ ([GitHub](https://github.com/stablyai/orca), [YC](https://www.ycombinator.com/companies/stably-ai-orca))。采配を主題にする同名はほかに 3 つあって、tmux で lead と worker を組む fmfsaisai/orca、コードに触れないオーケストレータを RL で訓練した Danau5tin の Orca-Agent、共有状態と人間チェックポイントを置く論文 ORCA がそれに当たる ([fmfsaisai/orca](https://github.com/fmfsaisai/orca), [multi-agent-coding-system](https://github.com/Danau5tin/multi-agent-coding-system), [arXiv 2508.21304](https://arxiv.org/abs/2508.21304))。3 つとも、采配役はコードに触らない、人間の関所を挟む、poll せず push で受ける、という結論に着いている。Captain と同じ形を別々の人が独立に選んだわけで、弱いながら裏付けにはなる。

本命の Orca は Electron 43、React 19、xterm.js、node-pty、Monaco で組んだデスクトップアプリに、iOS と Android のコンパニオン、ヘッドレスの `orca serve` が付く ([package.json](https://github.com/stablyai/orca/blob/main/package.json))。2026-03-17 の作成から 6 か月で **star は 72,853**、安定版は 282 本で、1 日あたり約 1.5 本出ている計算になる ([GitHub API](https://api.github.com/repos/stablyai/orca), [releases](https://github.com/stablyai/orca/releases))。本体は無料で、有料プランは見当たらない ([onorca.dev](https://www.onorca.dev/))。README の "69m downloads" は利用者数として読まない方がいい。v1.4.205 単体で自動更新用の `latest-mac.yml` が 2,269,013 回落ちているのに対し、DMG は 163,489 回だった ([releases API](https://api.github.com/repos/stablyai/orca/releases/tags/v1.4.205))。

管理の単位は worktree で、その中に 1 つの CLI エージェントと 1 つの端末を組にしたセッションを何本でも置ける ([agents-sessions.mdx](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/model/agents-sessions.mdx))。**ACP は使っていない**。リポジトリのコード検索で "Agent Client Protocol" は 0 件で、状態は端末の OSC タイトルと Orca が仕込む hook から取る ([code search](https://github.com/search?q=repo%3Astablyai%2Forca+%22Agent+Client+Protocol%22&type=code))。35 種前後のエージェントに対応を広げられたのは PTY 方式のおかげだが、代償は Herdr と同じ場所に出ている。Codex の起動バナーが idle 判定を通過する、Claude の起動が遅いと idle が誤って立って dispatch を失う、といった不具合と戦い続けている ([#15190](https://github.com/stablyai/orca/issues/15190), [#9976](https://github.com/stablyai/orca/issues/9976))。既定の権限は全バイパスで、docs は "The intent is that the worktree itself is the sandbox" と書きつつ、別のページでは "A worktree is an isolated checkout, not a security sandbox" と認める ([agents-sessions.mdx](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/model/agents-sessions.mdx), [supported.mdx](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/agents/supported.mdx))。承認待ちの列という発想が Orca に薄いのはこのためだ。

采配の層は、Herdr と違って存在する。2026-05 に Experimental で入った Orchestration は、Run、Task、Dispatch、Message、Decision gate を Orca のランタイムが永続化し、采配役は orchestration スキルを読んだ任意の CLI エージェントが `orca orchestration …` を叩く形をとる ([orchestration.mdx](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/cli/orchestration.mdx), [Discussion #681](https://github.com/stablyai/orca/discussions/681))。初期に作った組み込みスケジューラは捨てられ、`orca orchestration run` と `coordinator-start` は docs の言葉で "perform **no effects**" になった。采配役を、ただのエージェントとホストが持つ永続台帳と CLI で組む。この結論は Captain と同じで、Orca が一度作ったスケジューラを捨てた事実は、Captain を状態を持たない任命制のスレッドにした判断の追い風になる。

解けていないのは起こし方だ。Orca は idle の coordinator の PTY にメールボックスへのポインタを打ち込み、遅らせて Enter を送る ([mailbox-pointer-delivery.ts](https://github.com/stablyai/orca/blob/main/src/main/runtime/orchestration/mailbox-pointer-delivery.ts))。追跡 issue には、ポインタが人間の下書きに混ざる、Claude の AskUserQuestion に誤って答えてしまう、定期の heartbeat が coordinator のターンを浪費する、ready な仕事があっても idle の coordinator が起きない、が open のまま並んでいる ([#15190](https://github.com/stablyai/orca/issues/15190))。利用者は、25 分間隔のポーリングがそのまま死に時間になると報告した ([#4376](https://github.com/stablyai/orca/issues/4376))。necoder は台帳イベントを ACP の prompt ターンとして渡し、実行中はキューに積んで 1 通にまとめるので、誤配送も下書きの汚染も誤答も起きる場所がない。**Orca に対する一番大きな技術上の差はここにある**。もう 1 つの差は gate だ。Orca の Decision gate は coordinator が作る CLI オブジェクトで、誰が解決できるのかは一次資料で確認できなかった。worker は既定で YOLO なので、エージェントが worktree の中から `gh pr merge` を打つのを止める仕組みも見当たらない。統合と承認を権限として人間に残す設計は Orca にはない。

### 骨格は横並びで、差は采配役と統合の gate に出る

| | Herdr | Orca | necoder Fleet |
|---|---|---|---|
| 形 | Rust の TUI、1 バイナリ。client/server で SSH やスマホから再接続できる | Electron のデスクトップ、iOS/Android、ヘッドレスの `orca serve` | GPUI ネイティブのエディタの中の Fleet モード |
| ライセンス | Apache-2.0（2026-07-22 に AGPL から変更） | MIT | AGPL-3.0 |
| 管理の主語 | 端末（pane）と、その中で検出した agent | worktree と、その中の端末セッション | Task（1 Task = 1 worktree = 専用スレッド） |
| エージェントとの接続 | PTY。`--kind` は 24 種 | PTY。35 種前後。Claude だけ SDK 経路も育成中 | ACP の構造化イベント |
| 状態の権威 | Claude Code と Codex は画面スクレイピング。分からなければ idle か unknown | OSC タイトルと hook。idle の誤検出と格闘中 | ACP の permission 待ちとターン終了から necoder が導出 |
| 采配役 | なし。プリミティブだけ渡し、core に入れない方針 | Experimental の Orchestration。任意の CLI エージェントとスキルと永続台帳 | Captain。任命制の ACP スレッドと台帳と `necoder fleet` |
| 采配役の起こし方 | 利用者がポーリングを自作 | idle の PTY にポインタを打って Enter。誤配送が open | ACP の prompt ターン。busy 中は 1 通にまとめる |
| 承認 | 技術的な gate なし。同梱 skill が "ask the user before answering it" と書くだけ | 既定は全バイパス（Manual に切替可） | 要対応キュー。Captain は推薦のみ |
| 統合 | 機能なし。branch は決して消さない | hosted PR 経由。merge、auto-merge、stacked PR までアプリ内 | Conflict Radar のあと人間が Integrate |
| 未追跡ファイルと準備 | plugin の `worktree.created` イベント任せ | `.worktreeinclude`、`sharedDirectories`、setup hook | `.necoder/worktree-setup.sh` と `task.env` |
| 叩かれている所 | 状態の誤検出、多数同時稼働時の CPU、既読が軽すぎる | 編集が遅い、Electron の重さ、毎日リリースの揺れ | 市場の検証はこれから |

表の Herdr と Orca の列は両者のリポジトリ内の docs による ([SKILL.md](https://github.com/herdrdev/herdr/blob/master/skills/herdr/SKILL.md), [configuration.mdx](https://github.com/herdrdev/herdr/blob/master/docs/versions/0.9.1/website/src/content/docs/configuration.mdx), [worktrees.mdx](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/model/worktrees.mdx), [github.mdx](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/review/github.mdx))。

2026-09 時点で、並走管理ツールの画面は左に状態つきの一覧、中央に選んだ 1 本、という形に寄った。Conductor、Codex app、Claude desktop、Zed、JetBrains Air、Superset、Emdash、Devin がこの型で、外れているのはカンバンを既定にした Devin Desktop と Nimbalyst、ブラウザの板である Vibe Kanban くらいだ ([Conductor](https://www.conductor.build/docs/concepts/workflow), [Claude](https://claude.com/blog/claude-code-desktop-redesign), [Zed](https://zed.dev/blog/parallel-agents))。カンバンの評判は割れている。Vibe Kanban の作者は自分の Show HN で "~50% of the columns seem pretty redundant" と認め、Conductor は板にせずサイドバーを状態でグループ化する形に畳んだ ([Show HN](https://news.ycombinator.com/item?id=44533004), [0.35.0](https://www.conductor.build/changelog/0.35.0-workspace-status))。Fleet v2 の、左に Task 一覧、中央に 1 枚、並べるのは明示操作で 3 枚まで、という骨格は多数派と同じ場所にある。

差が付くのは采配役の扱いで、3 派に分かれた。製品が調整役を持つのは Devin の Managed Devins、Warp の `/orchestrate`、Augment Intent の Coordinator、Antigravity 2.0 の dynamic subagents など ([Cognition](https://cognition.com/blog/devin-can-now-manage-devins), [Warp](https://docs.warp.dev/platform/orchestration/), [Intent](https://www.augmentcode.com/blog/intent-a-workspace-for-agent-orchestration), [Antigravity](https://antigravity.google/blog/google-io-2026-feature-deep-dive))。API を開けて任せるのが Conductor、Superset、cmux、そして Herdr と Orca。持たないと決めたのが Emdash で、創業者は CLI 自身がエージェント間の調整をこなせるようになってきたから、と理由を書いた ([Show HN: Emdash](https://news.ycombinator.com/item?id=47140322))。Herdr と Orca は同じ 2 番目の派にいるが、Herdr は台帳を持たず、Orca は台帳まで持つ。

necoder にとって耳の痛い話が 2 つある。1 つは、Captain の売りだったエージェント非依存が薄まったこと。Conductor は 2026-08 に CLI と MCP を開け、エージェント自身が workspace を作り、送り、監視できるようになった。これはリリースノートの転載による二次情報だ ([Releasebot](https://releasebot.io/updates/conductor))。Warp も親と子で別の harness を使える。残る差は、役割と権限表と wake 条件を製品が定義していること、状態を台帳に置くので交代が自由なこと、統合と承認が人間だけに残ることに移った。もう 1 つは市場で、Orca への称賛にも批判にも orchestration はほとんど登場しない。利用者の大半は独立した N 体を自分で見張る使い方をしていて、采配役は一部のヘビーユーザーの領域にとどまる。Captain を Fleet の中核に置く賭けを、市場はまだ検証していない。FLEET-V2 §5.7 の「Captain 無しでも Fleet は成立する」は保険として正しい。

空いている席もはっきりしている。Orca への批判は、編集体験の弱さ（"I found editing experience too slow for daily use"）と、Electron の重さや毎日リリースの揺れの 2 本に集まる ([HN 49103047](https://news.ycombinator.com/item?id=49103047), [#6795](https://github.com/stablyai/orca/issues/6795))。どちらも GPUI ネイティブで本物のエディタを持つ necoder の土俵だ。並走 Task 間の衝突を統合前に予測する UI を第一級で持つツールは、今回調べた範囲では見つからなかった。各社は起きた衝突をエージェントに直させるか、PR の conflicts 表示にとどまる。見つからなかっただけで存在しない証明にはならないが、Conflict Radar は差別化点として残っている。

人間が現実に回せる数も揃っていた。Herdr の書き手は 2〜4 体、ヘビーユーザーで 5〜8 体。Superset のチームは 5〜7 体を "reliably" と書き、同じ記事で "most of our agents spend more time waiting for us to review their work than they spend doing it" と認めている ([HN](https://news.ycombinator.com/item?id=48714802), [Superset blog](https://superset.sh/blog/roadmap-to-100-agents))。最初に壊れるのはレビューの帯域で、次が、どれが自分を待っているかの把握、その次がマージ衝突、最後がマシン資源という順になる。各社が 100 体や fleets を掲げながら、並列数の中央値は 1 社も出していない。実利用の数が小さいからだろう。

両者から借りる細部は多くない。Herdr からは `fleet send` の意味論で、相手が blocked なら送らずに `agent_blocked` を返す、送信後 5 秒で活動が見えなければ `agent_prompt_stalled` を返す、timeout は未送信の証明にならないので再送前に読む ([agent-automation.mdx](https://github.com/herdrdev/herdr/blob/master/docs/versions/0.9.1/website/src/content/docs/agent-automation.mdx))。通知の節度も Herdr が磨いていて、1 秒後も同じ状態のときだけ通知する、見ている tab の分は鳴らさない、完了と入力要求で音を分ける ([configuration.mdx](https://github.com/herdrdev/herdr/blob/master/docs/versions/0.9.1/website/src/content/docs/configuration.mdx))。反面教師は既読の軽さで、見ただけで done が消えて完了を見失うという不満が 3 か月続いている ([discussion #864](https://github.com/herdrdev/herdr/discussions/864))。Fleet の Done は明示の確認で消し、確認済みを未確認に戻す操作も足す価値がある。Orca からは、`.worktreeinclude` を `.necoder/worktree-setup.sh` の前に読むこと（Claude Code と Conductor も読むので事実上の共通規約になりつつある）、diff の行コメントを貯めて 1 通で返すこと、Task の作成ダイアログを即閉じて背景で進めること ([worktrees.mdx](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/model/worktrees.mdx), [annotate-ai-diff.mdx](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/review/annotate-ai-diff.mdx), [Claude desktop docs](https://code.claude.com/docs/en/desktop))。Orca は一括で返す理由を "Sending comments one at a time causes the agent to swing back and forth" と説明している。

necoder の文書には直す箇所が 2 つ見つかった。FLEET-V2 §3.4 の「herdr の 3 本上限」と fleet-ux-2026-09.md の表は、Herdr の仕様ではなく、Zenn 記事の著者が自作の hook スクリプトに入れた閾値（152 桁の端末で 50 桁を 3 列）を Herdr の規則として読んだものだった ([Zenn](https://zenn.dev/gemcook/articles/herdr-worktree-parallel))。Herdr 本体は pane 数を制限しない。上限 3 という判断は変えなくてよいが、根拠は 1 利用者の経験則と necoder のカード最小幅、と書くのが正確だ。同じメモの「GUI 勢は誰もやっていない」も 2026-09 時点では言い過ぎで、VS Code の Agents window、Cursor 3 の Agent Tabs、Claude desktop が明示操作でのタイル表示を持っている ([VS Code](https://code.visualstudio.com/docs/agents/run/agents-window), [Cursor 3](https://cursor.com/blog/cursor-3))。既定が 1 枚である点は各社とも変わらない。

FLEET-CONTROL-PLAN の P7（Herdr を sidecar にして PTY とプロセス生存だけ任せる計画）には、今回の調査から注意点が出る。ここは調査で確認した事実に基づく私の推論だ。Herdr は pre-1.0 で、0.7.5 では `wait` が `agent wait` に、`agent send` が `agent send-keys` に置き換わったので、計画どおり版の固定が要る。`events.subscribe` は滞留が約 500 件を超えると黙ってイベントを落とすので、切断時だけでなく定期的にも snapshot と突き合わせないと台帳がずれる。`agent prompt --wait` は docs 自身が "It does not track individual turns." と書いていて、necoder 側で TurnId と generation を持つ計画は必須になる。常駐モードに「推定」の印を付ける判断は、Herdr の検出が画面スクレイピングである以上、正しい。

## 采配役で効いたのは中央の検証と外部の台帳で、壊れたのは自律マージと見回りだった

### 出荷された形は単一リードと深さ 1 の worker に寄った

2026 年に出荷された采配役は、単一のリードとフラットな worker という形に寄った。Claude Code の Agent Teams は "No nested teams" で lead は固定、Warp は "Orchestrations today are exactly one level deep"、Codex のソースは既定で深さ 1 と 6 スレッド（v2 は 4）を定めている ([agent-teams](https://code.claude.com/docs/en/agent-teams), [Warp](https://docs.warp.dev/platform/orchestration/), [config/mod.rs](https://github.com/openai/codex/blob/46aa019e805352c9d7fd9a740cbf7f8b9aeb162d/codex-rs/core/src/config/mod.rs))。2026-09 に beta で出た Cursor Projects は coordinator を "doesn't write code itself but directs other agents"、"never blocked and is always responsive to direction" と説明し、Claude Code の Projects は coordinator の会話が "sees what threads report back, not every step they take" だと書く ([Cursor Projects](https://cursor.com/blog/projects), [claude-projects](https://code.claude.com/docs/en/claude-projects))。再帰的な階層が実証されたのは、数百体を回した Cursor の研究ハーネスだけだ。任命制の単一リード、フラットな Task、入れ子なし、という Captain の形は主流の真ん中にいる。

捨てられた形の記録は Cursor が一番詳しい。対等なエージェントが共有ファイルとロックで自己調整する方式は、"Twenty agents would slow down to the effective throughput of two or three" で失敗した。楽観的並行制御に変えると今度は "agents became risk-averse" になり、難しい仕事を避けて小さく安全な変更ばかりするようになった ([scaling-agents](https://cursor.com/blog/scaling-agents))。計画、探索、spawn、監視、レビュー、編集、マージ、完了判定を 1 体に持たせた continuous executor は、勝手に眠る、自分で作業を始める、早すぎる完了を宣言する、という壊れ方をした ([self-driving-codebases](https://cursor.com/blog/self-driving-codebases))。Cognition の Walden Yan は 2025 年に "Don't Build Multi-Agents" を書いた本人だが、2026-04 の続編で立場を更新した。並列に書くスウォームには今も当てはまる、と断ったうえで、結論は "multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions"。任意のエージェント網が交渉し合う方式は "mostly a distraction" だという ([multi-agents-working](https://cognition.com/blog/multi-agents-working))。

長時間の運用に耐えた系は、例外なく采配役の記憶を会話の外に出している。Gas Town は identity と task を git に置いて "liberally kills off sessions and spins up fresh ones" とセッションを使い捨てにし、Claude Code の Projects は "recent messages, recent threads, and project memory rather than its full history" で動き、Factory は状態を複数のファイルに分けて "No single agent needs to hold the complete picture" と書く ([Appleton](https://maggieappleton.com/gastown), [claude-projects](https://code.claude.com/docs/en/claude-projects), [missions-architecture](https://factory.com/news/missions-architecture))。Magentic-One は台帳を外すと性能が 31% 落ちた ([Magentic-One](https://arxiv.org/html/2411.04468v1))。反対側の例が Agent Teams で、状態を lead のコンテキストに置いた結果、lead は交代できず、`/resume` しても teammate は戻らない。状態は台帳、スレッドはただの ACP セッション、という Captain の作りは、この系譜の一番純粋な形になっている。

起こし方も揃った。ハーネスが完了や失敗を検知して、リードの次のターンとして注入する。Agent Teams は "The lead doesn't need to poll for updates"、Codex はプロンプトで "Call wait_agent very sparingly." と指示し、Warp はメッセージと状態遷移に共通の連番を振って、親が結果のメッセージより先に `SUCCEEDED` を見ないようにしている ([agent-teams](https://code.claude.com/docs/en/agent-teams), [multi_agents_spec.rs](https://github.com/openai/codex/blob/46aa019e805352c9d7fd9a740cbf7f8b9aeb162d/codex-rs/core/src/tools/handlers/multi_agents_spec.rs), [Warp](https://docs.warp.dev/platform/orchestration/))。LLM 自身に見回りをさせる系からは、コストと律速の報告が続く。Gas Town の Witness は 1 周 30〜90 秒の patrol を単一スレッドで回し、設計文書が自ら "at high throughput it becomes a bottleneck" と認めた。実地では 60 分で約 $100、単位時間あたり通常の約 10 倍かかっている ([polecat-self-managed-completion.md](https://github.com/steveyegge/gastown/blob/main/docs/design/polecat-self-managed-completion.md), [DoltHub](https://www.dolthub.com/blog/2026-01-15-a-day-in-gas-town/))。

承認と統合には、はっきりした反証がある。Anthropic は Agent Teams、cross-session messaging、Projects の 3 か所で同じ規則を書いた。"A teammate can't approve a permission prompt or supply consent on your behalf" ([agent-teams](https://code.claude.com/docs/en/agent-teams), [cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging))。自律マージは DoltHub の体験記が一番強い材料で、"After the first PR got merged autonomously, despite the integration tests failing, I quickly closed Gas Town." のあと、同僚に `reset --hard` と force push を頼むことになった ([DoltHub](https://www.dolthub.com/blog/2026-01-15-a-day-in-gas-town/))。Cursor が integrator を "created more bottlenecks than it solved" として外した件は逆向きの証拠に見える。ただ、あれは数百体、グリーンフィールド、誤りを許して後で直す、という前提の話で、同じ続報が "a final "green" branch is needed" と認めている ([scaling-agents](https://cursor.com/blog/scaling-agents), [self-driving-codebases](https://cursor.com/blog/self-driving-codebases))。

### 研究の数字は中央の検証を支持し、分けすぎと代理承認を退ける

構成を揃えて比べた研究は Kim らの 1 本（preprint、260 構成を 6 ベンチマークで比較）で、Captain の形に有利な数字と不利な数字の両方を出している。有利な方は誤りの増幅で、独立に走らせるだけの構成が 17.2 倍に増幅するのに対し、**中央で確認する構成は 4.4 倍に抑えた**。不利な方はコストで、中央集権型はトークンが単一比 +285%、平均ターン数は 7.2 から 27.7 に増える。SWE-bench Verified では全てのマルチエージェント構成が単一エージェント以下（中央集権型で −3.1%）、単一の基準性能が 45% を超える課題では追加エージェントが負に働き、固定予算では 3〜4 体を超えると 1 体あたりの推論が薄くなりすぎる ([arXiv 2512.08296v3](https://arxiv.org/html/2512.08296v3))。Captain の wake を絞る作りは飾りではなく必須条件、ということになる。

協調コーディングそのものを測った CooperBench は厳しい。重なるコードに触る機能を 2 体に 1 つずつ渡すと、成功率は 1 体が両方やる場合より**平均 30% 低く**、人数を 2、3、4 体と増やすと 68.6%、46.5%、30.0% と落ちた。手数の最大 20% を連絡に使っても、全体の成功率は有意に上がらなかった ([CooperBench](https://arxiv.org/html/2601.13295))。反対側の証拠が CAID で、中央の委任、隔離した worktree、実行可能なテストで検証する統合を組むと、単一比で PaperBench +25.6 ポイント、Commit0 +14.7 ポイントだった ([CAID](https://arxiv.org/abs/2603.21489))。矛盾はしていない。CAID の課題は分解できて単一がまだ飽和しておらず、CooperBench は対等な 2 体が重なるコードを触る。Captain に一番近い直接の証拠は CAID だが、単一の preprint である点は割り引いておく。

委任文は、采配役の出力のうち一番てこが効く場所で、しかも LLM が一番苦手な場所だ。コンテキストを持たない subagent に何を伝えるべきかを測る PerspectiveGap で、33 モデルの平均合格率は **17.2%**（最良の GPT-5.5 で 62.0%）にとどまった ([PerspectiveGap](https://arxiv.org/abs/2606.08878))。Anthropic は委任に要る要素を objective、output format、道具と情報源の指針、task boundaries の 4 つと書き、Codex のソースは "decompose work so each delegated task has a disjoint write set" と指示し、Cursor は "Constraints are more effective than instructions" と書く ([multi-agent-research-system](https://www.anthropic.com/engineering/multi-agent-research-system), [multi_agents_spec.rs](https://github.com/openai/codex/blob/46aa019e805352c9d7fd9a740cbf7f8b9aeb162d/codex-rs/core/src/tools/handlers/multi_agents_spec.rs), [self-driving-codebases](https://cursor.com/blog/self-driving-codebases))。Cognition は manager の失敗として、"overly prescriptive" になること、子と状態を共有していると思い込むことを挙げた ([multi-agents-working](https://cognition.com/blog/multi-agents-working))。main に住んでコードを書かない Captain は、コードベースの細部を知らない。だから委任文は手順より、目的と制約と受入条件に寄せた方がいい。

検証は両刃だった。MAST は 1,600 超のトレースから 14 の失敗モードを取り出し、検証まわりの失敗が 23.5% を占めると報告した。検証役を置けば済む話でもなく、既存の verifier は "perform only superficial checks" にとどまる ([MAST](https://arxiv.org/html/2503.13657v3))。TeamBench では LLM の verifier が、決定的な採点で不合格の提出の **49% を承認**した ([TeamBench](https://arxiv.org/abs/2605.07073))。一方でコンテキストを共有しない検証役は効く。Factory の事例では validator が 81 件の問題を見つけ、修正が実装作業の 34.4% を占めた。Devin Review は PR あたり平均 2 件のバグを見つけ、実装役と "do not share any context beforehand" のときに一番よく効くという。どちらも自己申告だ ([missions-architecture](https://factory.com/news/missions-architecture), [multi-agents-working](https://cognition.com/blog/multi-agents-working))。読み合わせると、完了の判定はテストの終了コードのような環境の事実で行い、LLM のレビューは別コンテキストで知性を足す役にとどめる、になる。

代理承認を退ける数字もある。Claude Code の利用者は承認プロンプトの **93% を許可**していて、全件承認は疲労を生むだけだと Anthropic 自身が書いている。だからといって LLM に任せられるわけでもなく、専用の分類器でも実際のやりすぎ行動の 17% を見逃した（n = 52、自己評価）。ClawArena-Team では権限付与の精度が 50% を超えたモデルが 1 つもなかった ([auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode), [ClawArena-Team](https://arxiv.org/abs/2606.31174))。落としどころは、不可逆な操作だけ人間の gate にして、残りは事後に介入できる位置を確保することだ。Anthropic の計測では、API 経由のツール呼び出しのうち不可逆に見えるものは 0.8% だった ([Measuring AI agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy))。

Conflict Radar に直接関わる古い数字も 1 つ。Brun らが 9 つの OSS で測ったところ、VCS が報告するテキスト衝突は全衝突の 67% で、残りの 33% はクリーンと報告されたマージの中のビルド失敗とテスト失敗だった。クリーンだった関係の 20% は放置で衝突に悪化した ([Brun et al. 2011](https://homes.cs.washington.edu/~mernst/pubs/vc-conflicts-fse2011.pdf))。エージェントの PR でも、重なる PR 対のテキスト衝突率は同一エージェント同士で 19.8%、異種エージェント間で 41.7% と測られている ([arXiv 2607.04697](https://arxiv.org/html/2607.04697v2))。エージェント非依存の Fleet では異種の並走が普通に起きるので、高い方の数字が効いてくる。

コストの相場は単一比で 3〜10 倍（Anthropic の検証）、Agent Teams は plan mode で約 7 倍、Factory の mission は中央値で 12 倍 ([when and how](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them), [costs](https://code.claude.com/docs/en/costs), [missions](https://factory.com/news/missions))。それでも律速はトークンより人間だった。OpenAI のチームは "our bottleneck became human QA capacity" と書き、802 人と 196,212 PR を追った現場データでは、1 人あたりのマージ PR が 2.09 倍になる一方でレビュアー 1 人あたりの負荷がほぼ倍になった ([Harness engineering の保存コピー](https://jaytaylor.com/notes/node/1770842156000.html), [arXiv 2607.01904](https://arxiv.org/abs/2607.01904))。

## Captain は骨格を変えず、実装のずれを直し、検証と上限を足す

保つものから書く。コードを書かない単一リード、状態を持たないスレッドと追記専用の台帳、イベント駆動の wake、承認は推薦まで、Integrate は人間、digest だけ渡す、どのブランドでも任命できる、1 Task = 1 worktree で phase は necoder が導出する。ここまでは前節の証拠がそのまま支える。調べた範囲で necoder にしかなかったものが 2 つある。人間が Task に直接介入したことを台帳経由で Captain に知らせる `human_send` と、リードを状態ごと差し替えられる任命制だ。前者に当たる仕組みを文書化した製品は見つからず、Cognition が manager の失敗要因に挙げた、子と状態を共有しているという思い込みに正面から効く。Blocked を即時に上げず 15 秒待つ工夫も他に例がない。人間がすぐ答えた場合に Captain を起こさないのは、承認に人間が答える作りと噛み合っている。道具を CLI に寄せた判断も保ってよい。Anthropic は `gh` のような CLI の方が MCP サーバよりコンテキスト効率が良いと書いており、Codex は `codex mcp-server` を削除した ([costs](https://code.claude.com/docs/en/costs), [Codex MCP server removal](https://learn.chatgpt.com/docs/mcp-server))。ACP にはエージェント間の概念がないので、Captain と Task の関係は台帳と `necoder fleet` という necoder 固有の層で持ち続けることになる ([ACP overview](https://agentclientprotocol.com/protocol/overview))。

直すのは理念と実装のずれで、リポジトリで裏を取った（2026-09-20 の作業ツリー）。`wake_captain` は `ensure_named_thread` で同名の Captain スレッドを再利用し続けるので、wake のたびにプロンプトと現況表が積み上がり、コンテキストは単調に増える。状態が台帳にあるのだから、スレッドを捨てても失うものはない。ステートレスの配当をまだ受け取っていない状態だ。busy 中のイベントを溜める `captain_pending` は `Workspace` のメモリ上の `HashMap` で、necoder を再起動すると未配達の wake が消える。FLEET-V2 §5.6 が書く同一 Task の 5 秒デバウンスは `crates/workspace/src` に見当たらず、`TurnEnded` は即座に `wake_captain` を呼ぶ。Captain が idle のときに同じ Task から短い間隔で 2 件来ると 2 ターン使う。采配ログは `notifications.news` を読んでいて、台帳の `captain` イベントからは復元していない。

| 優先 | 何をするか | 根拠 |
|---|---|---|
| P0 直す | **Captain スレッドを交代させる。** N 回の wake かコンテキスト使用率の閾値で ACP の `session/new` に切り替え、現況は台帳から渡し直す。wake プロンプトは前半を固定し、イベントを末尾に足す | Cursor は "periodic fresh starts" がまだ要ると書き、Gas Town はセッションを使い捨てにする。入力が長いほど性能は不安定になり、キャッシュの有無で単価は 10 倍違う ([scaling-agents](https://cursor.com/blog/scaling-agents), [Context Rot](https://www.trychroma.com/research/context-rot), [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)) |

優先の理由を補っておく。P0 の 3 つは、ステートレスで権限を絞った采配役、という看板を実装が裏切っている箇所で、Captain を日常で回し始めるとコストと事故の形で表に出る。書かない規律については、Claude Code の docs も lead が "starts implementing tasks itself" を既知の癖として載せている ([agent-teams](https://code.claude.com/docs/en/agent-teams))。任意のブランドが Captain になれる以上、どれかは必ず書き始める。ACP クライアントである necoder は、これをブランドに依存せず止められる立場にいる。信頼できない入力（worker の出力）と状態変更（Task の作成と追撃）を扱うセッションに機微な権限を持たせない、という Meta の Rule of Two にも合う ([Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/))。ただし、各 ACP エージェントの編集系 tool call が必ず `session/request_permission` を通るか、`session/set_mode` にどこまで対応しているかは未調査で、実現性はそこで決まる。

足すものの中で一番効くのは委任文の型だと考えている。LLM が一番苦手で、しかも worktree と準備スクリプトと初回ビルドという空振りのコストが一番高い場所だからだ。分解案の事前承認も同じ理由で効く。FLEET-V2 §5.2 では Captain は無確認で Task を作れるので、Task 数と worktree 数とトークンが一気に増える唯一の操作に gate がない。既定を分けない側に置くことも同じくらい大事で、分けてよいのは、触るファイルが重ならないか、きれいなインターフェースで切れること、各 Task が自分のテストで独立に検証できること、順序の依存がないか `depend` で書けること、が揃ったときに限る。1 つでも欠けたら 1 Task にするか直列にする。並列が一番効くのは、調査、レビュー、バグの再現、競合する仮説の検証、互いに独立な小さな保守だ ([agent-teams](https://code.claude.com/docs/en/agent-teams), [Willison](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/))。

避けるものは次のとおり。自律マージ役と、人間 gate の段階的な緩和。worker 同士の自由な連絡と、共有ロックでの自己調整。横の伝達は Captain の `fleet send` と台帳で足りるし、digest に他の Task に影響する発見の欄を作れば、Cognition が未解決に挙げた "How does a child agent surface a discovery that should change its siblings' work?" への necoder なりの答えになる。LLM による見回りと役割の増殖もやらない。Gas Town の役割 7 種と heartbeat 3 系統は、コストと誤検知と "The number of overlapping and ad hoc concepts in this design is overwhelming." という批判を生んだ ([Appleton](https://maggieappleton.com/gastown))。同じ機能を設計役と実装役とテスト役に割るのも悪手で、引き継ぎのたびに忠実度が落ちる。例外はコンテキストを共有しない事後レビューだけだ ([when and how](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them))。Captain のターンを `fleet wait` で塞ぐのもやめた方がいい。wake がイベント駆動なのだから Captain はターンを終えればよく、塞いでいる間は人間の指示も届かない。worker の YOLO 既定、上限を Captain へのお願いで済ませること、Cursor や C コンパイラの設計を縮小して写すことも避ける。あれは誤りの許容、ほぼ完璧な検証器、グリーンフィールド、$20,000 規模のトークンが前提だ ([C compiler](https://www.anthropic.com/engineering/building-c-compiler))。最後に、並走できる数を Fleet の性能だと考えないこと。

## ゲームから借りるのは仕掛けで、衣装は着せない

### RTS の HUD と監督制御の人間工学は同じ結論に着いた

答えを先に書く。ゲームの類推は、機能の語彙を借りる範囲なら良い案で、製品をゲームとして着飾る方向は悪い案だ。necoder はすでに前者の側にいる。

RTS の HUD が多数ユニットの指揮に効く理由は絵柄にない。StarCraft II の公式ガイドを読むと、遊休ワーカーの件数が常時出ている、Ctrl+数字で割り当てた番号は動かず 2 度押しで視点が飛ぶ、通報には Space で飛べて 8 件まで履歴を戻れる、という仕掛けが並ぶ ([Blizzard](https://news.blizzard.com/en-us/article/4552955/game-guide-special-control))。necoder の ⌘⇧U、⌘1..9、要対応、トークン常時表示、⌘0 のブリッジはこの語彙とほぼ同型で、ゲームの見た目なしに大半をすでに持っている。

これを借りてよいと言えるのは、監督制御の人間工学が別の経路で同じ結論を出しているからだ。Olsen と Wood の fan-out は、1 人が回せるロボットの数を、放置できる時間を 1 回の介入にかかる時間で割った値で表す ([Olsen & Wood](https://dl.acm.org/doi/10.1145/985692.985722))。UI の仕事は介入時間を縮めること、Captain の仕事は放置できる時間を延ばすこと、と役割が分かれる。UAV 研究の相場は、直接の制御で 3 機、承認つき（management-by-consent）で 4〜5 機、例外時だけ（management-by-exception）で 8〜12 機、健全性の監視だけなら 15〜17 機。3 本の映像を同時に見る条件では、熟練オペレーター 10 人中 7 人が途中で降りた ([Porat et al.](https://pmc.ncbi.nlm.nih.gov/articles/PMC4878290))。舞台の上限 3 枚はこの数字と合う。Ruff らの比較では consent が手動にも exception にも勝っていて、Captain は推薦だけ、応答は人間、という現行の線を支持する ([Ruff et al.](https://direct.mit.edu/pvar/article-abstract/11/4/335/18417/Human-Interaction-with-Levels-of-Automation-and))。Lewis の整理に従えば、人間が自律的に協調する群と話すとき、負担は群の大きさに依らない O(1) になる。Captain の理論上の居場所はここだ。ただし Integrate と承認が人間に残るので、その分は O(n) のまま残る ([Lewis](https://journals.sagepub.com/doi/10.1177/1557234X13506688))。UAV からコーディングへの転用を直接確かめた研究はないので、ここは類推として読んでほしい。

同じ枠組みから、あまり愉快でない計算も出る。アラーム管理の規格は、操作者 1 人あたり長期平均で 1 時間に約 6 件が受容可能、12 件が管理できる上限、10 分に 10 件を超えたら洪水としている ([Chemical Engineering](https://www.chemengonline.com/alarm-management-numbers/))。5 体のエージェントがそれぞれ 10 分に 1 回承認を求めれば 30 件/時で、上限の倍を超える。Captain の推薦、常に許可、同種の承認を 1 枚に束ねる、は便利機能に見えて洪水を防ぐ必須部品だ。

知覚の研究からは、掟に直結する注意点が 1 つ出た。Healey の総説によれば、色相のばらつきは形の読み取りを妨げるが、逆は起きない。"Background variations in colour interfere with a viewer's ability to identify the presence of individual shapes"。周辺視で flicker の違いを見分けるには 100% 以上の周波数差が要る ([Healey](https://www.csc2.ncsu.edu/faculty/healey/PP/))。necoder の状態グリフはスレッドの識別色で描かれるので、行ごとに色相がばらつく。このばらつきが、どれが Blocked かという形の読み取りを邪魔しているおそれがある。打ち手は掟の内側にある。要対応を最上段に集める位置の符号化はすでにやっている。残りは、概観の面では状態グリフを中立色にして識別色のドットの隣に分けて描く、注意不要の Task は輝度を落とす、目立つ動きは Blocked の 1 種類だけにして Working は静かにする、の 3 つ。UI-SPEC §6 の「状態ドットは常にスレッド識別色」という明示判断に触れるので、先に実測した方がいい。Working 7 本と Blocked 1 本の画面で、composer を見ながら気づくまでの秒数を現行と中立色案で比べれば決まる。動きには規格の制約もある。WCAG 2.2.2 は 5 秒を超えて続く並行アニメに停止手段を求めているので、Blocked の脈動は数回で止め、形と位置を残すのが筋だ ([WCAG](https://www.w3.org/WAI/WCAG21/Understanding/pause-stop-hide.html))。VS Code が点滅カーソルの再描画だけで idle の CPU を 13% 使っていた件は、常時アニメが idle の予算に直結する実例になる ([vscode #22900](https://github.com/microsoft/vscode/issues/22900))。

### 衣装が効いた証拠はなく、逆向きの材料が並ぶ

Gas Town で一番評価が高いのは Mayor という単一の窓口で、批判者の Maggie Appleton も "With the Mayor as your single interface, that overhead disappears." と認める。一方で Mad Max の名詞については "this thing fits the shape of Yegge's brain and no one else's. I'd categorise that as a moderate design fail" と書いた。HN には、用語を orchestrator や worker pool や merge queue に訳し直して説明する人まで出た ([Appleton](https://maggieappleton.com/gastown), [HN](https://news.ycombinator.com/item?id=46458936))。構造は当たり、衣装は外れだった。Captain は Mayor の構造だけを取り、操作対象の語は Task、branch、worktree、Integrate と実物の名前のままにしている。今の方針が正しい側だ。

ピクセルオフィス系の Pixel Agents は GitHub で 9.3k stars を集めたが、Show HN は 3 points でほぼ無反応だった ([pixel-agents](https://github.com/pablodelucca/pixel-agents), [HN](https://news.ycombinator.com/item?id=49648023))。需要はある。ただし中身は愛着と楽しさで、監督の成績ではない。RTS を全面に出した VibeCraft の HN 投稿は 2 points、AgentCraft の効果は作者の自己申告だけで、Cursor 3 と Antigravity は素の一覧と受信箱を選んだ ([VibeCraft](https://news.ycombinator.com/item?id=45575842), [AgentCraft](https://gitnation.com/contents/agentcraft-putting-the-orc-in-agent-orchestration))。学術側で唯一の測定は ETH Zürich の AgentGUI で、理解課題が 38% 速くなり正答率が 80% から 93% に上がった（N = 8）。効いたのは activity feed とタイムラインで、ピクセルオフィスの比喩の効果は切り分けられていない ([AgentGUI](https://arxiv.org/abs/2607.26300))。Microsoft Research の調査は、行動トレースの UI が参加者の自信だけを上げ、最終的な正確さを改善しなかったと報告している ([Grunde-McLaughlin et al.](https://arxiv.org/abs/2602.16844))。きれいな可視化は過信を生む。要約の隣には必ず diff と実行ログへの 1 クリックを置くこと。

ゲーミフィケーションは、開発者の行動を歪めたという自然実験の証拠がある数少ない項目だ。GitHub が 2016 年に連続コントリビューション日数の表示を外すと、長い streak と、1 日 1 コミットだけの日が減った。論文の結論は "gamification can steer the behavior of software developers in unexpected and unwanted directions" ([Moldon et al. の要約](https://neverworkintheory.org/2021/10/03/how-gamification-affects-software-developers.html), [論文](https://johanneswachs.com/papers/msw_icse21.pdf))。トークンの棒は予算の可視化であって得点にはしない、という線を守る。

境界は Jakob Nielsen の一文で引ける。良い比喩は上達したら迂回できる足場で、"Failed metaphors often lock users into a single mode of interaction, becoming a prison" ([Nielsen](https://www.uxtigers.com/post/metaphor))。⌘⇧U は StarCraft を知らなくても、次の要対応へ飛ぶキーとして読めるから足場。歩くキャラで稼働を示すのは、その絵を読まないと状態が分からないから檻。迷ったら順に確かめる。その仕掛けは介入 1 回の時間を縮めるか、放置できる時間を延ばすか、状況認識（知覚、理解、予測）のどれかを上げるか。元のゲームを知らない人が画面だけで使えるか。UI 文字列に新しい名詞が増えないか。正常時に静かか。止まっているときに再描画を要求しないか。得点や順位や連続記録の形をしていないか。1 つでも引っかかれば外す。

### 編隊図は星型のままでは所属しか語らない

編隊図のようなグラフ表示は Captain と Fleet を一目で分からせるためにある、という作者の考えは半分当たっている。

当たっている半分は、概観の面が要るという点だ。Shneiderman の "overview first, zoom and filter, then details on demand" は今も有効で、Porat らの実験では、指揮地図に UAV 1 機につき 1 つのアイコンを置いて位置逸脱のアラートを足すと、経路逸脱の検知が平均 3 分から 5 秒に縮んだ ([Shneiderman](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf), [Porat et al.](https://pmc.ncbi.nlm.nih.gov/articles/PMC4878290))。調整役を持つ製品は例外なく調整役を特別な chat として見せていて、足している UI は Warp の pill bar、Devin の入れ子ツリー、Augment Intent の living spec くらいしかない。Orca では、orchestrator の下に worker を入れ子にしてほしい、worker のタブは隠したい、という要望が 3 か月 open のままだ ([#4374](https://github.com/stablyai/orca/issues/4374))。Gas Town をやめた人の一番具体的な不満も可視性で、いつマージされたのか、なぜ止まっているのかが分からなかった ([Tenzin Wangdhen](https://tenzinwangdhen.com/posts/gastown-good-bad-ugly/))。Captain の会話の隣に編隊図と采配ログを置くブリッジは、他社に欠けている部分を正面から埋めている。

外れている半分は、図の中身だ。ハブ表示は Captain を中心にした星型で、辺が運ぶ情報は、この Task は Captain の配下にある、だけ。位相としては所属以上を語らない。FLEET-V2 §3.3 には、旧仕様の編隊図が実機では常に畳まれ、画面が「ただのチャット」に見えていた、という記録が残っている。図が Fleet らしい絵であることは、開いておく理由にならなかった。足りなかったのは情報だ、と読んでいる。node-link 図が読みやすいのはおよそ 20 ノード以下の小さく疎なグラフで、Task 数が現実に 3〜10 の necoder はその内側にいる ([Ghoniem et al.](https://journals.sagepub.com/doi/10.1057/palgrave.ivs.9500092))。形式は合っている。だから押す方向は、絵をゲームっぽくすることよりも、次の 3 つになる。

1 つ目は、ノードを 1 Task = 1 タイルの情報タイルにすること。スロットは固定で、状態グリフ、名前と branch、context 使用量の棒、実行中のツールと経過、要対応マーカーと経過、`+N −M`、Captain が起動した印を載せる。レイドフレームが 5 人でも 40 人でも読めるのは、1 人 1 タイル、位置固定、連続量は棒 1 本、離散状態は決まった枠、注意不要は減光、という規律のおかげだ。WoW の UI mod 調査では、標準 UI を情報不足と答えた人が 2007 年に 78.4% いて、raid 系の mod は利用の多いカテゴリに入っていた ([Game Studies](https://gamestudies.org/1202/articles/ui_mod_in_wow))。ただしレイドフレームの設計原則そのものの出典はフォーラムとブログ止まりで、査読研究は見つかっていない。HP と違って context は増えると危険なので、満杯側に目盛りを打つ。棒の色はスレッド色のままでよく（UI-SPEC §1.3 でトークンメーターは許可済み）、閾値は色を変えずに目盛りと形で示す。

2 つ目は、辺に意味を持たせること。辺が情報を運ぶのはツリー表示だけなので、Task 間の depend と、統合済みか分岐中かの区別をそこに載せる。ハブ、扇形、ツリー、カードの 4 表示は同じ `fleet_lanes` を描いているので、タイルの固定配置と依存つきツリーの 2 つに絞る余地がある。これは私の推論で、Orca が競合から表面積が大きく足元が動くと評されていることと、necoder の、概念は Task とタブと Captain の 3 つ、という畳み方に沿わせた提案だ ([Nimbalyst](https://nimbalyst.com/blog/open-source-agent-workspace-alternatives-2026/))。

3 つ目は、Captain の発令キューを足すこと。発令、稼働中、待ち（誰の何を）、報告済みを並べ、`wait` と `depend` をそのまま描く。Endsley の状況認識の 3 段でいえば、知覚は状態グリフと要対応の件数、理解は digest と phase ピルが担っていて、necoder に欠けているのは予測、つまり Captain が何を出して何を待っているかだ。采配ログが過去の面なら、発令キューはこれからの面になる。

小さい話を 2 つ。⌘1..9 は FLEET-V2 の中で「Task 行 N へ」（§7）と「レールの並び」（§3.2 の F1 訂正）の 2 通りに書かれている。要対応の並び替えで行順が変わる一覧に連番を振ると、押した先が毎回変わる。StarCraft II の意味論に合わせるなら、番号は Task に固定で割り当て、2 度押しで composer に入る。遊休ワーカーに当たる手空きの件数は、Captain バーに静かに出すだけでいい。RTS の遊休は即損失だが、コーディングエージェントの Idle は指示待ちなだけで、重いのは Blocked の方だ。

命名は今の線で止める。海と空の比喩語は Fleet、Captain、ブリッジ、編隊、radar の 5 つで足りていて、操作対象と動詞は実物の名前のままにする。Gas Town は操作対象と動詞（bead、sling、convoy）まで比喩にして翻訳の手間を生み、Homebrew は一貫したビールの比喩でも語が増えた時点で "obtuse, and actively obfuscate package management concepts" と改名を求められた ([Homebrew #14912](https://github.com/Homebrew/brew/issues/14912))。コントロールグループやユニットフレームといった語は設計の会話と GLOSSARY の code 名にとどめ、UI 文字列には出さない。英語圏に出すときは、JetBrains に Fleet という IDE があった点だけ頭に置いておく。猫のマスコットはブランド、空状態、オンボーディングに置けば、Pixel Agents が見せた愛着の需要を安く取れる。状態の伝達路にはしないし、Captain をキャラクターにもしない。Nielsen は擬人化アシスタントについて "raises false social expectations, and feels condescending when suggestions miss" と書いている。

## 結論

3 つの問いの答えは同じ場所に集まった。足りない資源は人間のレビューと承認の注意だ。Herdr と Orca は端末と worktree の見通しを良くしてその手前までを解き、采配役の製品と研究は、書き込みは単線で知性だけ足す、に着き、ゲームの HUD と監督制御の人間工学は、介入 1 回を短く、放置できる時間を長く、に着いた。だから Captain の成績は、並走させた Task の数では測れない。人間が裁く 1 件あたりの手間がどれだけ減ったかで測る。necoder は台帳を持っているので、Blocked から応答までの中央値、1 時間あたりの要対応件数、wake あたりのトークン、統合後のテスト失敗を、体感に頼らず自分で取れる。イベント駆動、ステートレス、人間 gate つき、worker は異種の ACP エージェント、という形の coordinator を直接評価した研究は 1 本も見つからなかったので、この計測がそのまま necoder 自身の根拠になる。

結論を変えうる出来事は 3 つある。Herdr Cloud に orchestration が入ること。Orca が PTY への打ち込みをやめ、Claude の Stop hook か SDK の構造化セッションで coordinator を起こせるようになること（2026-09-11 に案が出ている）。ACP にエージェント間の概念が入ること（Proxy Chains の RFD はまだ Draft）([RFD updates](https://agentclientprotocol.com/rfds/updates))。どれも necoder の構造上の優位を縮める方向なので、四半期に 1 度は Herdr の CHANGELOG、Orca の #15190、ACP の RFD 一覧を見直すといい。それまでの間、ACP を権威にできることと、統合と承認を権限として人間に残していることは、PTY を選んだ両者が簡単には追いつけない場所にある。
